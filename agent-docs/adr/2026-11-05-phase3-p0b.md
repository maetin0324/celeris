# ADR 2026-11-05: 第 3 フェーズ P0-B — 達成判定の Rust の検証と mark_milestone の記録（[達成判定の不変条件](2026-11-05-phase3-achievement-invariants.md) への付記）

- 状態: 採用（実装済み）。task 01M6N7XY9H31GK4K0G0J1C6AQY。進捗は `agent-docs/progress/2026-11-05-phase3/p0b.md`。
- 対象: I1〜I4・I11（ケース K1〜K12・K41）。I5 以降は兄弟 task。

## 決定
1. **phase `achieved` は Rust が数え直す（I1）**。`project_proposal::validate` は TS の `gap` を達成の判定に使わない（Outcome が 0 件の `wait(achieved)` だけを `achieved_with_open_outcomes` で落とす）。decider（`project_decider_ts.rs` の `verify_achievement`）が `unverified_outcomes(snapshot, recorded)` で、各 Outcome に (1) I3 を満たす root が snapshot にあり、(2) 到達の記録があるかを確かめる。1 つでも欠ければ `wait(waiting)`（60 秒後に再評価）に置き換え、判断の行の `validation` を `pc/achieved-unverified:<未達の id,…>`、記録（`proposal_json`）の `achievement` に `recorded`・`unverified`・TS の `gap` を残す。
2. **到達の記録の正本（I2）**: approved の Roadmap がある案件は Roadmap の Outcome の最後の状態が `reached`。無い案件は、今の依頼文の版（`request_sha256`）での `mark_milestone` の判断で効果が `applied` のもの。`shadow`・`dry_run` は効果を書かない（`suppressed`）ので、その mode に限り `suppressed` の mark も記録に数える（enabled の判定には効かない）。
3. **mark_milestone は効果 `RecordOutcome` を持つ（I2）**。効果の時に `record_outcome` が根拠を今の store から確かめ直す。Roadmap がある案件は人の API と同じ `check_status` を通し、書き込みの tx の中で効果の門（`roadmap_effect_gate_open_tx`。A1 付記 11 と同じ門）を読み、Outcome の最後の状態が既に `reached` なら書かず、そうでなければ `record_status_tx`（actor `project_controller`、reason `pc-decision:<判断の id>`）で書く。検査に落ちれば tx ごと戻し、判断を `failed`（`effect_ref` = `refused:<code>`）にする。門が閉じていれば門に判断の記録を任せる（`suppressed`）。Roadmap の無い案件は、依頼文の Outcome と根拠の root を確かめ直し、`effect_ref` に根拠を残す。
4. **二重の記録 0（I11）**: 既に記録した Outcome への mark は効果なし（`pc/milestone-already-recorded`）。再起動の後は `outcome_in_place` が reason `pc-decision:<id>` の記録を見つけて `applied` にする。Roadmap の版の承認は既存の CAS（`base_version`）と human_epoch の bump で、古い判断の効果は門で止まる。
5. **到達の根拠（I3）は snapshot の root の行で決める**（`task_ops::project_snapshot::root_row`）。`reviewer_passed` は「最後の終端遷移が `review_pass` の done」かつ「最後の review の判定に不合格が無く、`Check::Command` の条件が全部合格の判定を持つ」ときだけ真。終端から非終端への遷移（reopen・retry）で前の合格と判定を捨てる。`ReviewerPassed` event だけでは真にしない。TS の `satisfies` は snapshot のこの欄を読むので、TS と Rust は同じ根拠を見る。
6. **repo の無い調査案件（I4）**: root に repo が無ければ、`integrated` は成果物があるときだけ真。成果物は、機械向けの file（`result.json`・`checkpoint.json`・`delegate.json`・`followups.json`）以外の `ArtifactProduced`、または合格の判定を持つ `artifact_exists`・`knowledge_page` の条件。依頼の自然言語の受入条件に hidden の oracle を要求しない。repo 付きの root は A9 D1 のまま `IntegrationMerged` だけ（K12）。

## 理由
- TS の bundle を書き換えても、Rust の数え直しと効果の時の確かめ直しを迂回できない（K1b・K4）。
- 到達の記録を効果の tx に置けば、判断と状態の書き込みが人の API と同じ検査を通り、二重の記録を tx の中の既存の記録で止められる。

## 採らなかった案
- **phase を書く tx（`project_controller_commit`）の中で数え直す**: commit は P1-G の持ち物の `store/project_wake.rs` にあり、task-core は task-ops の root の行の組み立てを呼べない。decide の時点の snapshot で数え直し、commit は既存の CAS（revision・human_epoch）に任せた。残る窓は未解決に書く。
- **SnapshotRoot に欄（`checks_passed`・`deliverable`）を足す**: TS の型・JSON schema・fixture の変更が広がる。既存の `reviewer_passed`・`integrated` の意味を I3・I4 に合わせて絞った。

## 旧い仕組みの扱い
- `to_decision` の `MarkMilestone` の「記録だけ（A5 の前）」の分岐を消した（効果 `RecordOutcome` に置き換え）。
- `validate` の `gap.open`・`gap.unknown` による達成の判定を消した。
- `root_row` の「`ReviewerPassed` が一度でもあれば合格」「repo の無い done は取り込み済み」を消した。

## 未解決
- decide と commit の間に root が reopen された場合、phase `achieved` が書かれうる（commit の CAS は revision・human_epoch だけを見る）。achieved の後は人の変更の wake でしか評価しない（A6 の guard）ので、自動では戻らない。P1-G の commit の tx に検査を足すか、root の reopen を wake にするかを決める必要がある。
