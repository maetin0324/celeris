# ADR 2026-11-05: pilot の公開 effect を worker の外の broker と daemon の承認 API で扱う（P0-D。[第 3 フェーズの不変条件](2026-11-05-phase3-achievement-invariants.md) への付記）

- 状態: 採用（実装済み。task 01M6N7XY9N8J21RRGC8AP6EZ4A）。
- 根拠: `agent-docs/progress/2026-11-05-phase3/p0d.md`（実行したコマンド・raw）。

[第 3 フェーズの不変条件](2026-11-05-phase3-achievement-invariants.md) の I10（効果の記録は worker の外）と K17〜K20・K25〜K28 を、
実 daemon の pilot（`scripts/dev/long-horizon-pilot/`）で満たす方式を決める。[A9 pilot の不具合の付記](2026-11-05-a9-llm-pilot-findings.md)
の D3 は「worker から書けない場所」の具体的な方式を実装 task に任せていた。この ADR がその方式である。

## 事実（main の起票時）
- `pilot_effect.py publish <id> --dir <dir>` は worker（stub）の process が記録 file に直接追記した。記録の場所は worker の引数に
  あり、worker は同じ uid で書ける。記録は読んでから追記し、lock が無かった。
- 承認は driver が `decisions/<id>.json` を書く擬似の operator で、daemon の承認 API を通らなかった。
- driver は `--effects-dir` と台本（`--effect-kinds`）を stub harness の command にだけ渡し、`--harness config`（実 LLM）の worker
  には command の場所も使い方も渡らなかった。
- 試験 daemon の worker の sandbox（ADR-0095 の DB guard）が読み取り専用にするのは DB と host の設定だけで、試行の home の下は
  worker から書ける。file の権限は同じ uid が chmod で戻せる。

## 決定
1. **記録を書くのは broker だけ**: driver が試行ごとに worker の外で `pilot_effect.py serve` を起こす。worker に渡すのは公開の
   command（`<home>/bin/pilot-effect publish <logical_id>`）だけで、これは abstract unix socket で broker に要求を送る client である。
   command は記録の場所を持たず、場所を渡す引数も受けない。
2. **改ざんは検出して試行を落とす**: 記録 `effects.jsonl`・`audit.jsonl` は HMAC-SHA256 の鎖で、鍵は driver が作って broker の stdin
   で渡す（disk に書かない）。audit の `published` の行は効果の行の MAC を持つ。broker は追記のたびに鎖の末尾を stdout の pipe で
   driver に知らせる。driver の collector は鎖・1 対 1・末尾を検証し、どれかが合わなければ facts を作らず observation_failed で
   試行を失敗にする。file は 0444・dir は 0555 にし、broker が書く間だけ開ける（偶然の上書きを防ぐ。防御の本体は 2 の検出）。
   改ざんされた記録では broker も以後の publish を断り（exit 5）、起動もしない。
3. **承認は本物の daemon API**: worker は承認が無いと exit 3 を受け、`pilot-effect:<logical_id>` を含む question で人に求める。
   question は daemon の `approvals` に 1 行入る（ADR-0033 D5）。driver は人の token で `POST /approvals/{id}/decide` を呼ぶ
   （台本の approve は `once`、reject は `denied`）。broker は `GET /approvals?project=` と task の `Answered` event を読み、
   主体が `human:` の決定だけを数える（CoS・operator の決定は承認にならない）。最後の人の決定が `once`・`standing` なら公開、
   `denied` なら exit 4 で効果 0。daemon が読めなければ exit 5 で効果 0。
4. **facts は独立に作る**: 承認（`human_ops` の approval、`faults` の approval_wait）は driver が DB の `approvals` から読む。
   効果は検証済みの broker の記録から読む。worker の自己申告（stub-run.jsonl・result）は facts に使わない。
5. **exactly once**: 判定と追記は thread の lock と record の flock の中で行う。追記は 1 回の write と fsync。追記の途中で落ちて
   末尾が欠けた行は、次の起動で切り詰めて audit に残す。効果の追記の直後に落ちて audit が無い場合は、次の起動で audit に
   `published`（`recovered`）を補う。どちらも効果は増やさない。
6. **worker への公開は案件の依頼文**: driver は C06 の案件の依頼文に公開の手順（Outcome ごとの command、exit 3・4・0 の意味）を
   書く。controller の root の objective は依頼文を含むので、実 LLM と stub の両方が同じ入口で読む。fixture（P0-C の持ち物）は
   変えない。
7. **stub 配線は残し、config harness の経路を足す**: `--harness stub` は台本（`--effect-kinds`）と `--effect-command` を引数で
   受ける従来の形を保つ。`--harness config-stub` は `--harness config` と同じ driver の経路に、objective だけを読む agent
   （`stub_harness.py --from-objective`）の TOML を渡す。LLM は呼ばない。
8. **旧い仕組みを消す**: `pilot_effect.py publish --dir`・`--unapproved`、`pending/`・`decisions/` の file、stub の
   `--early-publish`、`LONG_HORIZON_PILOT_STUB_EARLY_PUBLISH`・driver の `--stub-early-publish` を消した。承認前の publish は
   常に断られるので、「承認前に記録する陰性」は作れない。陰性は `LONG_HORIZON_PILOT_STUB_TAMPER=1`（worker が記録に偽の行を
   足す）に置き換えた。

## 試験
- `scripts/dev/long-horizon-pilot/test_pilot_effect.py`（15 件、偽の daemon API と本物の broker process）: K17（承認前・未決・
  別 id・人でない決定は exit 3 で 0）、K18（承認後 2 回で 1 件）、K19（その場の書き込みは権限で断られる、偽の行・書き換え・
  削除・両方の空化・別の鍵は検出、改ざんの後は publish を断り起動もしない、command は場所を持たず `--dir` を受けない）、
  K20（記録が無い）、K25（`denied` は exit 4 で 0、人の承認し直しは最後が効く）、K26（記録の前・後・途中で落ちて再実行して
  1 件、承認前の crash 地点は 0）、K27（並行の 2 本を hook で順序付けて 1 件）、daemon に届かない。
- `scripts/dev/test-long-horizon-pilot.sh` の段 2b: 単体試験、実 daemon の C06 を stub と config-stub で流す（o1 1 件、o2 0 件、
  承認 2 件、verdict pass）、改ざんの陰性（exit 1、observation_failed、facts なし）。

## 未確認・残り
- 実 LLM（`--harness config` の実 source）が依頼文の手順どおりに exit 3 で question を出すかは未確認（実 LLM は人が worker の
  外で流す。前の ADR の D9）。
- K27 の試験が main の `pilot_effect.py`（lock なし）で赤になるかは確かめていない。main の版は承認を file で待つ形で、新しい
  hook を持たず、同じ試験を当てられない。
- 鍵は driver の memory にあり、同じ uid の worker が driver の process の memory を読む（ptrace）ことは防いでいない。pilot の
  脅威（LLM の worker が記録を書き換える）には足りると判断した。
