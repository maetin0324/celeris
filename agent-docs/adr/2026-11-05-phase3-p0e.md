# ADR 2026-11-05: 第 3 フェーズ P0-E — pilot の root に公開契約の command check を結線し、判断の根拠を残す（[達成判定の不変条件](2026-11-05-phase3-achievement-invariants.md) I7〜I9 の実装）

- 状態: 採用。
- 根拠: `agent-docs/progress/2026-11-05-phase3/p0e.md`。前提は [A9 pilot の不具合](2026-11-05-a9-llm-pilot-findings.md) の D4。

## 結論
- Outcome block の 1 行に任意の `checks`（`{cmd, expect_exit}`）を足す。Rust が `launch_root` の効果を作るときに、対象 Outcome の `checks` を root の acceptance に `Check::Command` として足す。TS は command を作らず、見もしない。
- `Check::Command` の実行結果は新しい event `review_command_checked`（acceptance の index・command・期待 exit・exit・timeout・合否）に、`review_verdict` と同じ transaction で残す。
- pilot の driver は全 Outcome に公開契約の check を必ず付け、facts と ops に検査と reviewer の判断を写す。stub reviewer は確かめられない基準を pass にしない。

## 決定
1. **`checks` は依頼文の Outcome block に書く。** block は人が書く `Project.request` の一部で、controller は書き換えられない。ADR 2026-11-04-project-controller の「TS は決定的 check の command を作らない」を保つ（`RootCheck` は `reviewer`・`human` のまま）。`checks` は snapshot の JSON に出さない（`#[serde(skip)]`）ので TS の入力と schema は変わらず、TS が root の acceptance から check を落として迂回することもできない。TS の bundle は変えない。
2. **検査の優先の規則は変えない（I7）。** `review_task` は決定的な検査が落ちると reviewer を起こさず、`on_review_finished` は全 verdict の AND で done を決める。P0-E は、この規則が controller の達成まで届くことを本物の TS で固定する。
3. **出典は acceptance の index と command（I9）。** exit は判定文（`reason`）の文字列でなく、構造化した欄に残す。migration は要らない（event は JSON の追記）。必須検査（`[commands] check`）の合格を再利用した command は再実行しないので `exit` が `null` になる（合否は同じ束縛の `required_checks_evaluated` が根拠）。timeout と実行の失敗も `exit` は `null` で、前者は `timed_out` が真になる。
4. **driver の check の決め方。** `case.json` の Outcome に `checks` があればそれを使う。無ければ公開の文から導く: acceptance が `python3 minichunk.py verify <case> <id>` を書いていれば、commit された `out/<id>.txt` がその command の出力と同じこと。それも無ければ、依頼文が書く「成果は `out/<id>.txt` に書く」から、`out/<id>.txt` が commit されていて空でないこと。bench v2（P0-C）の全 19 Outcome は `checks` を持たず、acceptance の verify の手順から導く。公開 check の決定に非公開の材料（`oracle/<case>/oracle.json`、`oracle/holdout.json`、`grader/check_outcome.py`）を使わず、command にその canary と場所の名前（`oracle/`・`grader`・`check_outcome`）を入れない。`test-stub-reviewer.sh` が全 Outcome の command を検査する。
5. **stub reviewer。** 確かめられる 2 種類の基準だけ pass にできる。Outcome を名指す基準は、同じ review に合格した command check があり、候補の `HEAD:out/<id>.txt` が空でないこと。delivery が足す取り込みの判定は、head が base の子孫で `base..head` に commit があること。落ちた command check が 1 つでもあれば、どの基準も pass にしない。それ以外は理由付きで fail にする。「全基準を無条件に pass」は消した。
6. **別扱い。** repo の無い案件と自然言語のレビューは `checks` を要求しない（block の `checks` は任意）。repo の無い案件の根拠の規則は P0-B（I4）が持つ。

## check の無い経路で保証できないこと
`Check::Command` を持たない root（`checks` の無い Outcome、Roadmap の Outcome、人や CoS が起票した reviewer だけの task）について、Celeris は次を保証しない。done と達成は reviewer の判断だけに依る。

| 保証しないこと | 理由 |
|---|---|
| 成果が木に在ること、内容が契約を満たすこと | 決定的に確かめる処理が走らない。reviewer の LLM が読むかどうかは決定的でない |
| reviewer の判断の再現性 | 同じ入力で同じ判断になる保証が無い。`review_verdict.reason` は記録で、検証ではない |
| reviewer が実際に確かめたこと | reason は reviewer の自己申告。何を読んだかは run のログを読むしかない |
| 食い違いの検出 | `review discrepancy` の記録は、落ちた検査があるときしか出ない |
| oracle との一致 | oracle（`grader/check_outcome.py` の採点）は別の根拠で、check が公開契約を覆っていても一致は実測でしか分からない（I12、P0-F） |

check がある経路でも、check が見ない観点（読みやすさ、方針への適合、公開契約の外の正しさ）は保証しない。worker が検査の入力（repo の `minichunk.py` など）を書き換えた場合も、公開の check だけでは検出できない（採点の `grader/check_outcome.py` が別に確かめる）。

## 採らなかった案
- **TS が `RootCheck::Command` を作る**: TS が check を落とせるようになり、command を TS が組み立てることにもなる。規則に反する。
- **`ReviewVerdict` に欄を足す**: 既存の 65 か所の構築と照合に手が入る。command の記録は別の種類の事実なので event を分けた。
- **reason の文字列から exit を読む**: 文面の変更で壊れ、timeout と再利用を区別できない。
- **repo の `[commands] check` を使う**: Outcome ごとに分けられず、o2 の成果がまだ無い o1 の root が落ちる。

## 残した範囲
- Roadmap の Outcome は `checks` を持たない。approved の Roadmap がある案件の root は check の無い経路になる（進捗の「提案」）。pilot は Outcome block を使うので影響しない。
- 検査 script の中身は P0-C が持つ。
