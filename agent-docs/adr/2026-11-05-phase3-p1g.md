# P1-G: 自律復帰、brief の原子的 wake、案件 CoS の予算

## 決定
1. brief の内容が変わった場合だけ、保存と同じ transaction で controller の入力 epoch を進め、`external_released` の wake を書く。CoS の要約は人の回答ではないため `human_changed` にしない。同じ内容の再送は wake を増やさない。独立の保存口も immediate transaction を開始する。
2. 入力 epoch は既存の `human_epoch` を使う。これで snapshot の CAS と効果の transaction の門の両方が、brief 変更前の判断を拒否する。brief の変更だけでは blocked・paused・cancelled を解除しない。
3. 日次 token は task run と案件に属する chat run の input + output を数える。cache は従来と同様に加えない。chat 起動数を別に公開し、controller の入力数と同じものとして二重に加算しない。入力数と chat 起動数のいずれかが `max_cos_inputs_per_day` に達したら止める。

4. 自律復帰（K34・K35・K37）: `blocked` の案件は、最後の判断の行から止まった原因を決め、原因が解消したときだけ再開する（`crates/task-dispatch/src/dispatcher/project_resume.rs`）。再開は 1 つの immediate transaction の CAS（phase・`revision`・`human_epoch`・止めた判断の id・lease なし・案件が動いている）で、効果なしの判断の行（validation `pc/resume/<原因>`、schema `celeris.project-resume/1`、`basis` に根拠）を書き、`revision + 1`・phase `active`・`next_wake_at = now` にする。積もった wake は消費せず、次の評価が 1 回で畳む。判定・許可・予算の門はその評価で通常どおり掛かる。

   | 原因（判断の効果） | 解消（自動の再開） |
   |---|---|
   | TS の `escalate`（分類は `human_required` の既定の 7 種のどれか） | 問いの key に対する人の許可（`authority_answered`）、提案の却下（`authority_question_dismissed`）。`objective_change` は依頼文の変更も（依頼文を変えられるのは人だけ） |
   | `guard_same-failure` | 人の操作の wake（`human_changed`）か、失敗した root 自身の `root_done` |
   | `guard_ttl` | 外からの入力の wake（`is_external_input`: cron・停滞・`brief:`・`authority-denied:` 以外） |
   | `guard_budget` | 下の 5 |
   | `guard_invalid-proposals`・判定の失敗（`retry_count > 0`）・効果の失敗（`failed`）・分類できない止まり | 自動では解けない。人が mode を置き直す |

   人の pause・cancel は phase が `paused`・`cancelled` になり、ここを通らない。読めない値は再開しない（fail closed）。
5. 日次予算（K40）: guard が予算で止めるとき、その日の使用量を `Daily` と `Dangerous` に分ける。`Dangerous` は token が上限の 2 倍以上、CoS 入力・起票が上限を超えた、CoS の起動が上限の 2 倍以上のどれか（上限が効かなかった出来事）。`Daily` の止まりは次の UTC 00:00 を期限として `next_wake_at` に書き、notice に「次の UTC 00:00 に確かめる」と書く。期限の後、止めた日の使用量を数え直し（止めた後に走り切った run を含む）、危険でなく、人の操作の後かつ直近 7 日の自動の再開が 3 回未満で、起票の予算の止まりなら有効な `launch_root` の許可があるときだけ再開する。再開しないときは notice（`project_controller:budget_hold:<案件>:<判断>`）を 1 回だけ書き、期限を消す（人が mode を置き直すまで止まる）。同じ日に人が置き直してもまだ超過なら、同じ問いの notice は増やさずに `blocked` に戻す（guard の問いの notice が既にあり、判断の後に `revision` が進んでいないときだけ）。
6. 同じ失敗の問いの key は `same_failure:<署名>:<解消の時刻>` にする。解消（人の操作か再開の行）の後にまた上限まで失敗すれば、新しい問いを 1 回出して止まる。数え始めは最後の人の変更と同じ失敗の再開の遅い方。
7. 人の回答の待ち（K38）: TS の `POLICY.humanWaitSecs` を 6 時間から 1 日にし、答えのある問いの待ち（`ANSWERED_RECHECK_SECS`）も 1 時間から 1 日にする。人の回答・操作は wake で届くので、timer は取りこぼしの照合だけでよい。今日の CoS 入力の上限による待ちは `dailyLimitRecheckSecs`（6 時間、従来の値）。cron の `project_reconcile` は、phase `blocked` の案件と、人だけを待つ待ち（`waiting_on` が全部 human、または `pc/authority-answered`）で `next_wake_at` の前の案件には wake を積まない。
8. TTL の「外からの入力」から CoS 自身の brief の更新（`brief:`）と daemon の内部の wake を外す（`project_controller_last_input_at` と guard の両方）。CoS の要約の更新で人の待ちの TTL は延びない。
9. 人の提案の却下は同じ transaction で `human_epoch` と wake を進める。人が許可を取り消したときも同じ（CoS・operator の取り消しは数えない）。
10. 計測: `GET /projects/{id}/controller` に `budget_today`（day・cos_inputs・roots・tokens・chat_starts）を足し、案件の画面に今日の使用量を出す。

## 範囲外
- 実 LLM の確認と 24〜72 時間の実稼働は人の gate（A9 の手順）。この変更は仮想時刻と fake・本物の bundle の試験だけで確かめた。
- `pc/no-progress` の止まりは、問いへの人の回答（許可・却下）でだけ解ける。進捗の増加での自動の再開はしない。
