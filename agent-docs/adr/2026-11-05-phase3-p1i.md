# ADR 2026-11-05: 第 3 フェーズ P1-I — 長時間運用の計測を 4 条件で揃え、V8 heap を RSS と分けて読む

- 状態: 採用。
- 根拠: `agent-docs/progress/2026-11-05-phase3/p1i.md`。前提は [TS 制御層の境界](2026-11-02-ts-control-layer-boundary.md) (f) の RSS の上限、[project controller](2026-11-04-project-controller.md) A6 の資源の raw、2026-11-04 の本番の観測（`agent-docs/progress/2026-11-03-ts-control-ops/p1e-shadow-measure.md`、RSS 181,820 kB → 588,668 kB／26 分）。

## 結論
- `ScriptRuntimeHandle::heap_stats()` を足す。actor の制御の channel（`Control::HeapStats`）で今の generation の isolate の `GetHeapStatistics` を actor の thread で読み、`HeapStats`（used・total・physical・external・malloced・native context 数・generation 番号）を返す。`RuntimeStats` には入れない（watch の購読者を heap の変化のたびに起こさない）。
- 長時間の計測は 1 条件 = 1 process で、`off`（`[script]` なし）・`v8_load`（isolate を起こすが mode rust）・`shadow`（`lane_rules` compare）・`enabled`（`lane_rules` ts）の 4 条件に同じ負荷を流す（`crates/celeris/tests/long_run_soak.rs`、`scripts/dev/long-run-soak.sh`）。project controller の mode（`off`・`shadow`・`enabled`）は仮想時刻の 72 時間で揃える（`project_controller_soak_72h_*`）。
- 24/72 時間の実時間の実稼働は人の承認があるときだけ行う。承認の無い run は仮想時刻・replay・数十分の非本番の計測までにとどめ、実稼働は未実施と書く。

## 決定
1. **heap は制御の channel で読む。** `Control` は queue の満杯に関係なく届くので、判定の要求で詰まっていても計測できる。actor が止まっていれば `None`。V8 の platform・isolate の作り方・heap 上限・watchdog は変えない。判定の呼び出しの経路にも触れない。
2. **条件は process で分ける。** RSS は process で一度増えると戻りにくく、同じ process で条件を続けると前の条件の分が混ざる。nextest は試験ごとに process を分け、`long-run-soak.sh` は test binary を条件ごとに別 process で同時に起こす（nextest の 10 分の打ち切りを避ける）。
3. **負荷は件数で決め、CPU を焼かない。** dispatch の間を `LONG_RUN_SOAK_PACE_MS` で空け、過去の event の行（`LONG_RUN_SOAK_SEED_EVENTS`）で DB の大きさを本番に寄せる。LLM は呼ばない（fake harness の `sh`）。既定は test-affected 向けの小さい値（3 cycle × 2 件、seed 1,000 行）。
4. **本番の観測と同じ式・同じ区間で並べる。** 本番の 4 標本（02:40:43Z からの 0・600・1,200・1,529 秒）を `long_run_soak_summary.py` に定数で持ち、試験の標本から同じ経過秒に最も近い点を取って、どちらも 2 点の差 ÷ 時間で傾きを出す（全区間 0→1,529 秒は本番 935.5 MB/時、定常 600→1,529 秒は本番 746.9 MB/時。MB は 1,024 kB）。本番比は同じ指標どうしの比だけを出す。最小二乗の傾きは本番の 4 標本と比べられないので出さない（付記 attempt 2: attempt 1 は本番の 2 点の傾きと試験の最小二乗の傾きを割っていた）。
5. **計測の窓の中で restart しない。restart は run を持ったまま止めて測る。** 窓の中の dispatcher と isolate は 1 個のまま（本番の 26 分の観測と同じ）。restart は窓の後に同じ DB で、run とリースを持つ別 process（同じ test binary の `long_run_soak_lease_holder`）を SIGKILL し、daemon と同じ孤児の回収（`OrphanTakeover`）で回収の時間を測る。止める前に running の run とリースが 1 以上あることを assert し、無ければ集計も exit 2 にする（付記 attempt 2: attempt 1 は run の終わりを待った後に restart し、回収の対象が 0 だった）。

## 揃えられない条件（明記する）
- 本番は `cos_digest` も compare だった。試験の dispatcher は CoS chat の pipeline を持たないので `lane_rules` だけを比べる。
- 本番は API・web・cron・chat・実 worker（claude 等）・ssh の背景の仕事を同じ process で持つ。試験は `build_dispatcher` の dispatcher と fake harness だけ。
- 本番の DB は events 783,007 行（2026-11-04）。試験は 200,000 行を seed した。

## 却下した案
- **`RuntimeStats` に heap を入れる**: `publish` のたびに値が変わり、`watch_stats` の購読者（試験の出来事待ち）を余計に起こす。
- **`celeris::run`（daemon 全体）で回す**: isolate の handle に外から触れず、V8 heap を読めない。API の待ち受けも要る。heap を読むために daemon に計測の API を足すのは、この task の範囲（計測）を超える（提案に残す）。
- **restart を同じ process の中で dispatcher を捨てて行う**: 捨てた dispatcher の run の future が同じ process で動き続けて結果を書き、持ち主の消えた run にならない。pid も同じなので孤児の判定（`pid_alive`）が働かない。
- **実時間の 24/72 時間をこの run で回す**: 人の承認が無い。run の壁時計（2 時間）にも入らない。
