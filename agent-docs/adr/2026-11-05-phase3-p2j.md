# ADR 2026-11-05: 第 3 フェーズ P2-J — controller の GET と画面に要約（未達・達成・待機の理由・承認の範囲・次の wake・上限・追跡）を出す

- 状態: 採用。
- 根拠: `agent-docs/progress/2026-11-05-phase3/p2j.md`。前提は [project controller](2026-11-04-project-controller.md) A1・A6・A7・A9、
  [達成の不変条件](2026-11-05-phase3-achievement-invariants.md) I1〜I4、[P1-G](2026-11-05-phase3-p1g.md)。

## 結論
- `GET /api/v1/projects/{id}/controller` の `ProjectControllerView` に `summary: ProjectControllerSummary` を足す
  （`outcomes`・`outcomes_invalid`・`waiting`・`authority`・`next_wake`・`budget_limits`・`trace`）。組み立ては
  `task_ops::project_controller_view::summary`。案件の画面の「自動運営」はこれをそのまま出す（数え直さない）。
- 要約は画面の写しで、判定の入力にしない。判定は今までどおり tick ごとに snapshot から Rust の guard と TS が決める。

## 決定
1. **到達は判定と同じ関数で数える。** `recorded_outcomes` を `task_dispatch::project_decider_ts` から
   `task_ops::project_controller_view` へ移し、dispatcher（I1 の `verify_achievement`）と API の要約の両方がこれを呼ぶ
   （写しを 2 つ持たない）。効果の JSON は `{"kind":"record_outcome","outcome_id":…}` を読む（task-ops は task-dispatch に依存しない）。
   snapshot は `project_snapshot::build` で作り、`reached` = 到達の記録あり かつ `root_satisfies` の root が 1 件以上
   （`unverified_outcomes` と同じ規則）。
2. **待機の理由は最後の判断の規則から決める。** phase が `waiting`・`blocked`・`paused`・`cancelled` のときだけ出す。
   `kind` は判断の行の `validation`（最終の規則）の接頭辞（`pc/guard/`・`pc/authority-required`・`pc/achieved-unverified`・
   `pc/script-unavailable`・`pc/invalid`）、どれでもなければ効果が `open_escalation` か案が `escalate` なら `escalation`、他は `wait`。
   `details` は判断の記録（guard の名と detail、TS の `wait` の待ち相手、`escalate` と `open_escalation` の問いの key と要約、
   未達の id）から 1 行ずつ。
3. **承認の範囲は authority ledger の生きている許可だけ。** `authority_section`（snapshot）と同じ `grant_denial` で絞り、
   `launch_root` の判定（`authority_check`）の結果と理由を一緒に出す。
4. **上限は daemon の起動時の `[project_controller.budget]`。** `ApiState::with_project_controller_budget` で渡す
   （budget は再起動で変わる欄なので reload を考えない）。今日の使用量は既存の `budget_today`。
5. **追跡は最後の判断の行の写し。** `decision_id`・`rule_id`・`mode`・`effect_state`・`effect_ref`・`based_on_revision`・
   `snapshot_sha256`・`generation_id`・`decided_at`。全文は `GET …/controller/decisions`。
6. migration・event の種類・schema（`docs/api/v1/api-v1.schema.json`）は変えない（`ProjectControllerView` は schema の生成の対象外）。

## 却下した案
- **画面で `proposal_json` を読んで数える**: 到達の規則（I1〜I4）を TS の画面にもう 1 つ持つことになり、Rust と食い違う。
- **要約を判定の後に DB に保存する**: 状態の写しが増え、判定と保存の間で古くなる。GET のたびに store から作る。
- **新しい endpoint（`…/controller/summary`）**: 画面は既に `GET …/controller` を読んでいる。応答を 1 つにした。
