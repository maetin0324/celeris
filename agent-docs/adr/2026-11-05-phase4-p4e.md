# P4-E 統括 CoS の旧新 paired 比較の固定・runner・採点

P1-H（`2026-11-05-phase3-p1h.md`）の契約を引き継ぎ、実 LLM の比較を人の承認だけで始められる状態にする。実 LLM はこの決定の範囲で起動しない。

## 決定
- D1 腕の固定: 旧腕は main の first-parent で件名が「a4: 統括 CoS の相談・短い読取・委譲」で始まる最古の commit の親、新腕は測定時の HEAD。`tests/fixtures/general-cos-eval/arms.json` が規則を持ち、`compare.py pin` が rev・件名・skill（`config/skills/cos-operator`・`cos-inbox-triage`）と prompt の source の内容 hash・binary の sha256 を manifest に書く。旧腕が A4 の `consult.md`・`chat/intent.rs` を持つか、新腕が持たない場合、pin は失敗する。skill は試行の一時 KB に arm の rev から `git archive` で置く。現行 binary の controller off で旧腕を代用しない（P1-H と同じ）。
- D2 試行: 1 試行で一時 home・一時 DB・loopback の daemon を新しく作り、統括 thread に課題の 1 発言だけを送る。初期状態は CoS を止めた daemon で人の API と stub worker から作る（seed の通知で CoS が実 LLM を消費しないため）。その後 CoS を有効にして再起動し、静かになってから基準（message の seq・run・task）を記録する。終わりは「返事があり CoS が静か」、delegate は「起票した task の終端と、その後の返事」、上限は 1 試行 600 秒。終わりの後に 5 秒続けて静かになるまで待ってから集める（壁時計には含めない）。host の release 置き場と disk 監視は試行の dir に向け、host の受信箱項目を試行に入れない。
- D3 計画: 8 課題 × 2 腕 × 2 回 = 32 試行。repeat 1 は旧→新、repeat 2 は新→旧の順で、順序の効果を打ち消す。両腕で model・account・harness・権限（同じ `--llm-config` と `--cos-route`）・初期状態・課題（`cases.json` の hash）を同じにする。
- D4 dataset `p4e-v1`: `read-three` の初期状態を `[done, failed, ready, done]` から `[done, failed, cancelled, done]` に変えた。`ready` は試行の daemon が実行してしまい、両腕で同じ初期状態にならない。各課題に `seed` を持たせた。
- D5 実 LLM の門: `--tier llm` は preflight が次を全て満たすときだけ動く。Celeris の worker の run の外（`CELERIS_RUN_ID` が無い）、人の承認 file（`approved_by` が `human:` の主体、`approved_at`・`account`・`model`・`harness`・`limits` の 4 上限）、`--llm-config`、pin 後の binary・`cases.json` が不変、計画が対になっている、出力が本番の dir の外。runner は承認と `limits.json` の小さい方を上限にし、token（input+output+cache read+cache creation）・壁時計・USD の累計のどれかが上限に達したら、残りの試行を始めない。USD は CoS と worker・reviewer の全 run の `usage.cost_usd`（task_core の静的単価表の推定で、請求額ではない）の合計で数え、`cost_usd` の無い run を含む試行が 1 件でもあれば費用の上限を守れないので止める（`usd_unknown`、fail closed）。`approved_by` は `human:<名前>`（空白・`:` を含まない名前）の形だけを通し、それ以外（`claude`・`reviewer`・`operator:…` 等）は拒否する。
- D6 採点: 原票（raw）から腕を伏せた採点票（blind id、対応表は別 file）を作る。読取・委譲・拒否と権限の欄は原票の事実で決まるので、決定的な採点器（`deterministic:p4e-auto/1`）が埋める。相談の欄（分析・提案・追問・深さ 0〜3）は文の質の判断なので人が埋める。CoS・agent・worker を名乗る採点者は拒否する。採点の欄が残る試行は観測にしない（欠測）。実 LLM の段でも、決定的な採点は一次の検査であり、独立の採点者が確認する。
- D7 集計 v2: `general_cos_eval.py` を `celeris.general-cos-eval/2` に置き換えた（v1 の行は拒否）。指標は v1 の runs・tool_calls・wall_seconds・tokens（input+output）・cost_usd に、first_reply_seconds、cache_read_tokens、cache_creation_tokens、handoffs、human_interventions を足した。相談には consult_depth を足した。課題種別ごとの成功率と、paired の新 − 旧の差を出す。stub の usage は欠測（null）で、0 にしない。
- D8 handoff と人の介入の数え方: handoff は試行の後に元の thread に入った system の入力・知らせの数（経路の表示「CoS 実行経路」を除く）。人の介入は課題の 1 発言で、runner は追加の介入をしない。CoS の token は全 thread の CoS chat run の合計で、worker・reviewer の run の usage は `worker_usage` に別に残す。

## 範囲外
本番の DB・config・daemon・release・systemd には触れない。旧 milestones API の 410、human_required、許可の保護、TS と Rust の分担は変えない。K2・K4・IEEE Access の凍結評価には触れない。
