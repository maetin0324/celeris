# Jev 分類段の daemon 配線

設計は ADR `2026-10-15-jev-wire`。WU ごとの記録は `2026-10-15-jev-wire/<wu>.md`（jev-key・jev-tick・jev-e2e）。

## 実装の要点

- `[jev]`（既定無効・未知欄はエラー）→ `SecretsDirKeyProvider`（secrets dir の `jev_api_key`、値は出さない）→ `ClassifyTick`（`Dispatcher::tick` の直前に ready の WU を分類して `ClassificationBoard` へ）。
- dispatcher・store に Jev / HTTP / LLM 呼び出しは無い（board を読むだけ）。鍵未登録・401/403 は既存の `apply_lane_assist` → `enter_credential_wait`。429・5xx は fixed へ戻る記録で、鍵再登録は要求しない。
- `routing.mode` は変えない（本番 `fixed` のまま）。

## 一連試験（jev-e2e）

`crates/celeris/src/daemon/classify_tick/e2e.rs`。`build_dispatcher`・`ClassifyTick::build`・`JevClassifier`・`SecretsDirKeyProvider` は本番と同じ。Jev は 127.0.0.1 の fake HTTP server、通知は fake webhook、鍵の検証だけ mock。

- `unregistered_key_waits_notifies_then_resumes_once_and_classifies`: 未登録 → credential 待ち（Jev へ 0 回・run 0 本・受信箱 1 件）→ 通知 1 件（再 tick でも増えない）→ 鍵登録 → 検証 1 回・同じ WU が一度だけ再開 → Jev へ 1 回（Bearer 付き）で `JevOk` → 同じ fingerprint の再保存・再 tick でも再開・分類・通知は増えない。鍵の値は events / notifications / 通知本文に出ない。
- `rate_limit_never_becomes_a_credential_wait`: 429 → `fell_back_to_fixed{rate_limited}`、`credential_waits` 0、受信箱 0、鍵要求の通知 0、Jev へ 1 回のみ（再分類・再試行なし）。

## 本番への移行

release.sh・verify.sh・昇格・本番 config の書き換え・鍵登録は worker は行っていない。以下は運用セッションと人が行う手順。

### config の差分

- **何も書かなければ挙動は変わらない**（`[jev]` 既定 `enabled = false`、`routing.mode = fixed`）。release の昇格だけでは分類は始まらない。
- Jev を有効にするとき `~/.config/celeris/config.toml` に追加するもの:

```toml
[routing]
mode = "decision_assisted"   # fixed のままなら分類は呼ばれない

[jev]
enabled = true
# 以下は既定値と同じなので省略可。変えるときだけ書く（未知欄は読み込みエラー）
# endpoint = "..."            # http(s) のみ
# model_id = "..."            # `~` の latest alias は不可
# timeout_ms / max_retries / backoff_base_ms / backoff_max_ms
# cache_max_entries / breaker_failure_threshold / breaker_cooldown_ms
# secret_id = "jev_api_key"   # secrets dir 内の名前（値ではない）
```

- `[llm_sources.jev]` は**不要**（ADR jev-wire D5。Jev は harness の LLM source ではなく分類 API。source として宣言すると route 選択の候補に混ざる）。
- `[secrets] dir` が設定済みであること（鍵の読み先）。`[notify]` の webhook が設定済みなら、鍵未登録の待ちで通知が出る。
- `routing.mode` を全体で `decision_assisted` にするかは人の判断。対象を絞る切替が要るなら ADR 付記で提案する（今回は実装していない）。

### 鍵登録の手順

1. config に上記を足し、daemon を reload（または再起動）する。`[jev]` が変わると分類段が作り直される。
2. 鍵が未登録のまま ready の WU が出ると、その WU だけ `waiting_for_auth` になり、受信箱に credential 待ちが 1 件、通知が 1 件出る。
3. Web / GUI のアカウント画面（`/accounts`）から secret `jev_api_key` に Jev の API キーを登録する（`PUT /api/v1/secrets/jev_api_key`）。
4. 登録後、検証 1 回で待っていた WU が一度だけ再開し、次の tick で分類される。受信箱 item は消える。
5. 確認: `GET /api/v1/secrets` で `jev_api_key` に `fingerprint` があること、受信箱に credential 待ちが残っていないこと。鍵の値はどの出力にも出ない。

### ロールバック

`[jev] enabled = false`（または節を消す）と `routing.mode = "fixed"` に戻して reload。登録済みの鍵は消さない。
