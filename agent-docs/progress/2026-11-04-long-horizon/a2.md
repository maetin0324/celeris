# A2 TS の Project Controller core（snapshot→gap→次の行動の proposal）

完了日: 2026-11-04

## 結論
- control-ts に領域 `project_controller` を足した。入力は Rust の `ProjectSnapshot`、出力は `ProjectProposal`（continue・replan・launch_root・wait・escalate・mark_milestone）。TS は DB も system も書かない。
- task ledger（`Project.request` の Outcome block と root の acceptance）と progress ledger（root の状態・合格・取り込み・失敗の分類・待ち・過去の判断）は `task_ops::project_snapshot::build` が store から毎回作る。独立の Goal・別のイベントストアは足していない。
- Rust の検証 `task_core::project_proposal::validate` が起票の前に proposal を当てる（based_on・acceptance の縮小・Outcome の所有・paused・上限・根拠の root）。
- 非本番 E2E（本物の bundle を本物の V8 で、一時 DB）で root1 完了→中間目標 o1 到達→root2 起票（root1 は done のまま）→最終目標 o2 到達→追加の起票 0、同時 8 評価・8 適用で root 1 件を確かめた。
- TS だけの 1 行の変更で `ts-verify.sh --record` は cargo 0 回・link 0 回。edit→activate の warm p50 は 8.715 秒（20 試行）。

## 方針（TS の判定の順）
1. 案件が active でない → wait。2. Outcome block の形の誤り → escalate 1 回、以後 wait。3. Outcome なし → replan(no_outcomes) を request の版ごとに 1 回。4. 到達した Outcome を mark_milestone（記録が先）。5. 全部到達 → wait(achieved)。6. 人の待ち → wait。7. 進行中・取り込み待ちの root → continue。8. 依存の済んだ次の Outcome を選ぶ。9. 直前の試行が review 不合格 → replan 1 回、基盤の失敗 → wait（1800 秒）、他の終わり方 → escalate 1 回。10. 試行の上限 → escalate、日の上限 → wait。11. launch_root（acceptance は Outcome の文のまま、`continues_root_ids` で先の root を結ぶ）。
到達の判定（D6）は「done・合格・取り込み済み」かつ「Outcome を名指す」か「acceptance を文字どおり全部含む」。Rust の `root_satisfies` と TS の `satisfies` は同じ規則。

## ADR からの変更（ADR に付記した）
- snapshot に `outcomes_invalid` を足した。`SnapshotDecision` に `reason_code`・`outcome_id`・`request_sha256` を足した（同じ版での replan・escalate の繰り返しを TS が避けるため）。
- `RootSpec.acceptance[].check` は `reviewer`・`human` だけ（TS は command を作らない）。
- Host op `project_controller:read_root_evidence` は作っていない（下の未解決 1）。

## 未解決と次の gate
1. Host op `project_controller:read_root_evidence`（capability・scope）は未実装。A2 の判定は snapshot だけで決まり、op を要しない。別案件の root は snapshot に入らず（`evidence_scope`）、別案件の root を指す proposal は Rust の検証が `milestone_evidence_unknown`・`unknown_root` で拒否する（s11）。成果物の中身を読む判定が要るときに A3 が足す。
2. 判断の記録・revision・human_epoch・CAS は A1 の表の代わりに試験の harness が持つ。本番の接続（`dispatcher/project_decider_ts.rs`、Proposal → `ProjectEffect`）は A3。
3. `integrated` は「repo の無い root は done で取り込み済み、repo のある root は `IntegrationMerged`・`IntegrationNotApplicable` の event」で判定した。`task_integration_state` の表と `auto_integrate` 無効の merge candidate は見ていない。
4. 失敗の分類は「`review_fail` の遷移なら review_failed、他の failed は infra」。予算切れ等の細分は A6。
5. `script-compare.py` は `proposal_only` を数えない（project_controller の compare は A3 の接続の後）。
6. 測定は in-place の編集と復元（edit-activate-baseline.sh の既存の方式）で、使い捨て worktree ではない。
