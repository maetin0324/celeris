# A3 案件 CoS の主体的運営を A1/A2 に結線（dry-run/shadow/enable/rollback）

完了日: 2026-11-04

## 結論
- A1 の durable wake の判定の口に A2 の TS（領域 `project_controller`）を繋いだ。`TsProjectDecider` が snapshot → TS →
  Rust の検証 → runaway の上限 → 効果（root の起票・案件 thread への system 入力・人への escalate の notice）を作る。
- 判定（次の行動・失敗の分類・質問の要否・CoS 入力の上限での待ち・進捗なしの停止）は TS にあり、規則の 1 行の変更で
  判定が変わることを本物の bundle で確かめた（Rust は同じ binary）。
- review 不合格の後の輪を閉じた。決定的 check が落ちた root は CoS に聞かずに次の試行の root を起票し、それ以外は案件 CoS に
  1 回だけ頼み、brief が書き直されるか待ちの時間が過ぎたら次の試行を起票する。試行の上限で人に 1 回 escalate する。
- 案件 CoS が依頼文・objective/acceptance・controller の起票・本番 promote・外部公開（PR の merge）・不可逆な操作
  （repo・account・組織・skill の削除、案件の取り消し）を独断で行えないことを 422 の試験で固定した。
- 既定は本番で無効のまま（`[project_controller]` が無ければ controller は入らない。入っても案件 mode `off`・領域 `rust` では
  TS を呼ばない）。本番の config・DB・release は触っていない。

## 変更の要点
- 効果の対応: `continue`・`wait`・`mark_milestone` → 効果なし（`next_wake_after_secs`・phase `waiting`/`achieved`）、
  `replan` → `QueueCosInput`（key `pc-input:<案件>:<revision>:<reason>`、本文は「人の指示ではない」と id・分類だけ）、
  `launch_root` → `CreateRoot`（A2 の `launch_root_spec`、key `pc:<案件>:<root key>`）、`escalate` → `OpenEscalation`。
- 既存機構の再利用: wake・lease・CAS・効果の門は A1、snapshot・検証は A2、CoS の起動は既存の案件 thread の system 入力、
  知らせは notice、拒否は `/cos/operations` の監査（`rejected`）。tree の continuation・children_wait は触っていない
  （TS は進行中の root を `continue` で見守るだけ）。受信箱の代答は既存の 7 類型の basis が無ければ断られる（試験で確認）。

## dry-run（attempt 2 で直した）
attempt 1 の review は「mode `dry_run` が TS を呼ばず、運用者が dry-run を使えない」「422 の文が存在しない op
`project.controller_report` を案内する」で差し戻した。attempt 2 で次のように直した（ADR 付記 A3 の 7）。
- 人が mode を `dry_run` に置くと、同じ tx で wake `dry_run:<revision>` を 1 件積み、次の tick で TS を 1 回呼ぶ。もう一度は
  既存の `POST …/controller/wake`。判断の行は mode `dry_run`・効果 `suppressed` で、`GET …/controller/decisions` で見られる。
  event・cron・人の発言の wake は積まず、timer・phase も置かない。起票・CoS 入力・LLM は 0。
- 試験だけが呼んでいた `TsProjectDecider::dry_run` は消した。
- 422 `project_controller_owns_launch` の文は `project.status_put` か人の発言の取り次ぎを案内する。
- 試験: `project_cos_dry_run_on_request`（task-dispatch、tick を通す）、`project_cos_dry_run_mode_is_human_requested`
  （task-api、人だけが置ける・CoS は 403・人の発言では評価しない・wake で再度頼める）、`project_cos_ts_dry_run_compare_domain`
  （celeris、本物の bundle を領域 `compare` で呼ぶ）。

## attempt 3 で直したこと
attempt 2 の review は次の 3 点で差し戻した。
1. 外部公開・不可逆な操作の拒否が無い（criterion 7）。controller が `off` でない案件の案件 thread の run が `instructed_by`
   無しで行う `task.pr_merge` を 422 `external_publication_requires_human`、`repo.delete`・`account.delete`・`org.delete`・
   `skill.delete`・`project.cancel` を 422 `irreversible_requires_human` で断るようにした（ADR 付記 A3 の 10）。
   `goal_guard.rs` の冒頭の誤った説明も直した。試験は `project_cos_refuses_production`（6 件の拒否と、`instructed_by`
   を引けば門を通ること）と `project_cos_irreversible_gate_only_in_autonomy`（`off` では当たらない）。既存の試験
   `project_wake_api_human_cos_is_not_counted` は、shadow の案件で CoS が案件を取り消す経路が 422 になったので期待値を直した。
2. review 不合格の後に修正の root へ進む経路が無い（criterion 6）。TS（`decide` の 9）を次のように直した（ADR 付記 A3 の 9）。
   - 分類 `worker_bug`（決定的 check の失敗）: CoS に聞かず、次の試行の root（`outcome:<id>:<n+1>`）を起票する。
   - それ以外: `replan` を 1 回出し、brief の `updated_at` が判断より新しくなるか、`humanWaitSecs`（6 時間）が過ぎたら
     次の試行を起票する。起票する root の objective に、前の root の id と分類、brief に CoS の続け方があることを書く。
   - 直前の root が試行の上限なら CoS に聞かず `attempts_exhausted:<id>` で人に escalate する（待ち続けない）。
   - root_done の CoS への指示に、enabled の案件では「次の root は controller が起票する。判断は brief に書く」を足した。
   試験: vitest 4 件、`project_cos_ts_review_failed_retries_after_brief`（本物の bundle。replan → 待ち → brief の更新 →
   `outcome:o1:2` の起票 → 2 回目の不合格で `pc/attempts-exhausted`）、`project_cos_root_done_tells_the_cos_the_controller_launches`。
3. dry_run が event から写した外部待ちの解除（cluster job・browser）でも評価していた（副次の不備）。
   `ControllerMode::accepts_wake` に `from_event` を足し、`dry_run` では `source_event_id` のある wake を積まない。
   `project_cos_dry_run_on_request` に確認を足した。

## 未解決
- brief の更新は wake を積まない。CoS が brief を書いた後の判定は、待ちの timer（残りの時間）か CoS・人の
  `POST …/controller/wake` で起きる（skill に書いた）。brief の更新で wake を積むかは A6 か A9 で決める。
- `task.pr_merge` 等の拒否は controller が `off` でない案件の案件 thread の run だけ。統括 CoS と `off` の案件は従来の gate。
- escalate の後は phase `blocked` で、人が mode を置き直すまで判断しない。人の受信箱の回答で自動に戻す経路は無い。
- `runaway_guard` と TS の `pc/no-progress` は A6 の `max_no_progress_decisions` の guard と同じ上限を使う。A6 は
  `dispatcher/project_guard.rs` に移すときにこの 2 つを 1 つにまとめる。
- mode `dry_run` の判断も `revision` を進める。`dry_run` の間の人の操作は `human_epoch` だけ進み、判定は起こさない。
- `release.promote` の拒否は controller が `off` でない案件の案件 thread の run だけ。`off`・状態行なしの案件と統括 CoS の promote は既存の gate のまま（test-affected の 1 回目で、既存の試験 `cos_ops_admin_config_daemon_and_external_effects_run_once` が案件 CoS の promote を使っていて落ちたので、I13 に合わせて範囲を絞った）。
