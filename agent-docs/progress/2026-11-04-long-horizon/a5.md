# A5 Project Roadmap（版付きの途中目標を、旧 milestones を復活させず現行設計に統合）

完了日: 2026-11-04

## 結論
- 案件に紐づく版付きの Roadmap を足した。版は提案（`proposed`）として積まれ、人の決定だけが今の版（`approved`）を進め、
  前の版は `superseded` になる。CoS・operator は決められない。
- Outcome は版をまたいで不変の id・acceptance・priority・depends_on を持ち、状態（`open`・`in_progress`・`reached`・`dropped`）、
  evidence、担った root の一覧と記録の履歴を持つ。`reached` は root の evidence を Rust が確かめたときだけ。
- 旧 milestones・project_plan の 410 は変えていない（既存の試験 6 件が通る）。`milestones` 表・`Task.milestone_id`・
  ExecutionPlan の stage・WorkUnit の phase を読まない。brief（全置換の要約）と Roadmap は別の表で、brief の書き込みは版を変えない。
- approved の版があれば controller の snapshot は request の block の代わりに Roadmap の Outcome を読む。

## 必要性（A2・A3 の PoC の raw を読んだ結果）
実装の前に、A2 の e2e の raw（`a2/e2e/*.jsonl`、33 行）と A3 の raw（`a3/*.jsonl`、27 行）を読んだ。request の block だけでは
次の 4 点が足りなかった。

| 不足 | raw の証拠 |
|---|---|
| Outcome の版が無い | A2 の 33 行の欄は `action・applied・cos_inputs・escalations・extra・gap・llm_launches・roots・roots_total・rule_id・schema・snapshot_sha256・step・test` だけで、途中目標の版や承認を表す欄が無い。途中目標の集合は request の全文の hash でしか区別できない |
| 到達が残らない | `mark_milestone` 4 行のうち 3 行は `applied: {"recorded":"mark_milestone"}`（判断の記録だけ）、1 行は `milestone_evidence_unknown` で拒否。到達（`gap.reached`）は判断のたびに root から計算し直し、Outcome の状態として残らない |
| root との対応の履歴が無い | A3 `review_retry.jsonl` は同じ `o1` に 2 回目の root（`retry_key_suffix: outcome:o1:2`）を起票した。どの root が `o1` を担ったかは冪等キーの記録にしか無く、Outcome の側から読めない |
| 途中目標の変更を人に確かめる経路が無い | A3 `refusals.jsonl` の `project_cos_refuses_request_edit` は 422 `project_request_human_only`。CoS は block を書けず、変更を提案して人の確認を記録する場所も無い。A2 `s8_no_outcomes` は block が無いと `replan(no_outcomes)` の後 `wait` を繰り返す（3 行） |

この 4 点は Roadmap の版・Outcome の記録・提案と決定で埋まる（下の試験で確かめた）。不要とは判断しなかった。

## 未解決と次の gate
1. controller の `mark_milestone` を Outcome の記録に結ぶ効果は未実装。今は記録の route が人だけで、controller の判断は
   従来どおり記録だけ。A6 以降で `ProjectEffect` に足し、効果の tx から `task_ops::roadmap::record_status_tx` を呼ぶ。
2. TS（`control-ts/src/domains/project_controller.ts`）は snapshot の `roadmap.outcomes[].status` を読まない。到達は root から
   計算し直す。人が記録した `reached` を TS が使うかは方針の変更として TS-only で足せる（cargo 0）。
3. `check_status` の evidence の確認は書き込みの tx の前の読み取りで行う。確認と書き込みの間に root が reopen されると
   古い確認で記録しうる（窓は 1 回の HTTP 要求の中）。
4. 案件画面への結線（`project-detail-view.tsx`）と gateway の経路の確認は A9。web の生成型は使わず panel に型を書いた
   （DTO を api schema に載せていないため）。
5. A7 の authority と同じ案件で approve と grant を束ねるかは決めていない。

## 本番への移行
- promote で migration 0113 が表を 2 つ足す。既存の行は変えない。config の欄の追加・削除は無い。
- release を戻すときは SCHEMA_VERSION 113 の DB を 112 の binary が開けない（`SchemaTooNew`）。手順は `docs/ops/project-controller.md` の節「Roadmap」。

## 提案
- Roadmap の `reached` を人が記録したら controller の wake を `human_changed` で起こしている（`human_epoch`）。A6 で
  `mark_milestone` を結ぶとき、人の記録と controller の記録が食い違った場合は人を優先する規則を ADR に足す。
