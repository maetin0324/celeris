# A6 長時間実行の運用（event 主 + cron の照合、controller の phase、予算・guard、fault injection と仮想時刻の replay）

完了日: 2026-11-04

## 結論
- controller は event（root の終了・失敗、人の操作、外部の解放）で起き、cron の `project_reconcile` は event を取りこぼしたときの照合として働く
  （試験 `event_primary_cron_fallback`: event の経路は 31 秒、event を落とした案件は次の正時の cron で 1 回だけ評価して回復）。
- controller の phase（`active`・`waiting`・`blocked`・`paused`・`achieved`・`cancelled`）は Task の running と独立に、`project_controller_state` の
  1 列だけで持つ。`paused`・`cancelled` は `Project.status` から毎 tick 同期し、止まっている間の wake は評価せずに捨てる。`achieved` は人の
  変更でだけ評価する。
- 判定（TS の isolate）の前に Rust の guard を掛ける: 同じ失敗の繰り返し・TS の案の検証落ちの連続（品質）・1 日の CoS 入力・起票・token の予算・
  外部の応答の TTL。当たれば判定を呼ばずに人に 1 回だけ知らせて `blocked`（無限の再試行なし。不要な Manager〈案件 CoS〉の起動もしない）。
  next-wake（timer）と同一 event のまとめ（coalesce・wake key の一意）は A1 のものを使い、3 日の時計の飛びでも評価は 1 回に畳まれる。
- fault injection と仮想時刻の replay の試験 13 件（task-dispatch）と、本物の V8 の資源の測定 1 件（celeris）を足した。100 案件で isolate は 1 個、
  thread も増えない。LLM は呼ばない。複数日の実稼働は A9 の別 pilot に残す。
- 本番の config・DB・release・daemon には触れていない。既定は全案件 `off` で、この変更は `[project_controller] enabled = true` の daemon でしか動かない。

## 変更の要点
- guard の判断は既存の tx1（`project_controller_commit` の CAS）で書き、効果は既存の `OpenEscalation`（notice と `blocked` を同じ tx）を使う。新しい
  表・別のイベントストア・task の状態機械は足していない。migration なし。
- 同じ失敗の署名は wake の種類と失敗の理由の文（空白を畳み、連続する数字を `#` に）の sha256 の先頭 16 桁で、理由の文そのものは判定に使わない（I11）。
  数える範囲は最後の `human_changed` の wake の後。人の変更がその評価の wake に入っていれば掛けない。
- 予算の日は UTC。CoS 入力・起票は `applied` の効果だけを数える（`suppressed`・`failed` は LLM も root も起こしていない）。token は案件の task の run の
  `usage_json` の input + output（`tree_metrics::RollupMetrics.tokens` と同じ規則）。
- TTL は phase `waiting` で、評価の wake が cron だけ（か timer）のときに、cron 以外の最後の wake（無ければ最初の判断）から数える。
- 見つけた既存の穴: `OpenEscalation` の効果の後・`applied` の前（B5）で落ちると、`blocked` の門で `pending` のまま残っていた。notice の有無で `applied`
  にする（試験 `crash_each_stage` の AfterEffect で再現し、直した）。

## 未解決
1. 予算の超過・TTL は `blocked` にして人が mode を置き直すまで止まる。日が変わっても自動では戻らない。毎日自動で戻すかは人が決める（提案 1）。
2. 同じ失敗の数え方は案件の wake の全件を読む（`project_wakes_all`）。失敗の wake が来たときだけ読むが、長期の案件で wake の行が増えると遅くなる。
   wake の行の掃除（消費済みの古い行）は A1 にも無い。
3. TTL の「最後の入力」は cron 以外の wake の時刻で、`stagnation` の wake も入力に数える。停滞の検出が繰り返すと TTL が延びる。
4. `paused`・`cancelled` の間の wake は捨てる。再開の後は snapshot（状態）から判定するので失う情報は無い想定だが、停止中の event の種類は判断の
   記録に残らない。
5. token の予算は案件の task の run の和で、案件 CoS の chat run（`chat_runs`）の token は入っていない。
6. 資源の測定は 100 案件までで、複数日の RSS の推移は測っていない（A9 の pilot）。
7. `achieved` を置くのは TS（`WaitPhase::Achieved`）だけで、Rust は Roadmap の全 Outcome が reached かを照合していない（A5 の `mark_milestone` の効果も未実装のまま）。

## 提案
1. 予算の超過は「次の日の 0 時 UTC に `waiting` へ戻す」選択肢を config に足す（今は人が置き直すまで止まる）。人が決める。
2. `GET /projects/{id}/controller` に `budget`（今日の使用量と上限）と `guards`（最後に当たった guard と問いの key）を足す。使用量は
   `task_ops::project_budget::usage` で API からも読めるので、dispatcher の memory は要らない。loop cost は `daemon_snapshot` に載せる。
3. 消費済みの wake の行を一定期間で消す掃除（events は追記専用のまま、`project_wakes` は派生なので消せる）。
