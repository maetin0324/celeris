# A7 許可範囲の authority ledger と human escalation policy（fail closed・偽の人の指示の防止）

完了日: 2026-11-04

## 結論
- 案件・途中目標（Roadmap の Outcome）・作業単位（task）の範囲ごとに、人が与えた許可を authority ledger（表 `authority_grants`）として持ち、
  Rust が判定する。許可は人の token だけが作り、元の根拠（人の発言・人の決定・人の承認・永続の認可・人の mode 操作）・期限・回数が必須。
- `human_required`・`destructive`・`production`・`api_authorization`・`external_publish`・`opaque_external_effect` の 6 分類は、許可が無い・切れた・
  根拠が読めない・範囲が不明・前の使用の結果が不明のどれでも拒否する（fail closed）。`human_required` は許可にできない。
- controller が `off` でない案件の案件 CoS の `/cos/operations` は、分類のある操作を人の発言の引用か有効な許可が無ければ 422 で断り、
  許可で通すときは回数を 1 回消費する。controller の続きの root の起票（`launch_root`）も許可を要し、無ければ人に 1 回だけ聞いて止まる。
- 人に聞き直さない: 提案（`authority.grant_propose`）は同じ問いを 1 回だけ通知し、人の答えの後は根拠を示して 409 で断る。controller の
  `escalate` も同じ問いに人の答えがあれば聞かずに根拠を記録する。
- 監査（`authority_audit`）に suggestion・observed outcome・actual actor・human decision を残す。
- 本番の config・DB・release は触っていない。既定は全案件 `off` で、この機構は動かない（I13）。

## 変更の要点
- 判定の順（`check_tx`）: 分類が不明 → 拒否、`human_required` → 拒否、範囲が案件に無い → 拒否、同じ案件・同じ分類に結果 `unknown` の使用 →
  拒否、候補（同じ分類で範囲を含む許可。狭い範囲・近い期限の順）の中で取り消し・期限・回数・根拠を確かめて最初に通るもの。無ければ
  最も新しい候補の拒否の理由。
- 偽の人の指示の防止: 許可の作成は `Principal::Human` だけ（operator は 403、CoS の credential は直接の route で 422
  `cos_audit_context_required`、`/cos/operations` では EXCLUDED）。根拠の発言は `role=user`・author `human:`・取り次ぎでない・同じ案件か統括の
  thread。CoS の文・system 入力・統括 CoS の proposal の転送・operator の投稿・author の無い行・他の案件の発言・ログの文・予約の種類は 422。
- 無条件の許可にできない: 期限（366 日以内）と回数（1〜1000）は必須で、表の trigger が書き換えを断る。CoS の既存の不変条件
  （`instructed_by` の確かめ、`human_required` の 403、basis の検査、A3 の拒否）は変えていない。分類のある操作は autonomy の中で前より厳しくなった
  （許可か人の発言の引用が要る）。
- 途中目標の範囲（final review の差し戻しの修正）: `scope_exists` の `ScopeKind::Outcome` は `project_snapshot` と同じ規則で、approved の Roadmap の版が
  あれば取り下げていない Outcome の id だけを有効とし、request の block を読まない。版が無ければ block を読む。読めない版は `Err`（判定は
  `ledger_unreadable`、作成は 500）。取り下げた Outcome の許可は `authority_answered` からも外した。旧い block だけの判定は消した。
- 既存機構の再利用: `/cos/operations` の監査（`rejected` の行）、notice（`feed::record_in_tx`）、A1 の wake・`human_epoch`・効果の門、
  A3 の escalate の notice と `blocked`、`instructed_by` の確かめ。新しい状態機械・イベントストアは足していない。

## 未解決
1. **解決**: 途中目標の範囲を A5 の Roadmap に結線した（`store/authority.rs` の `scope_exists`。ADR 付記 A7 の 13）。controller の `launch_root` と人の許可の
   作成は approved の Roadmap の Outcome で通る。
2. 承認・永続の認可の行には決めた主体の欄が無い。「CoS が `instructed_by` 無しで決めた記録が無い」で人のものとみなしており、operator の
   token で直接決めた承認は人の決定と区別できない。区別するには `approvals` に `decided_by` を足す migration が要る。
3. `/cos/operations` の門と結果の記録は同じ tx ではない。間で落ちると監査の行は `unknown` のまま残り、同じ分類の次の操作は止まる（安全側）。
   その知らせ（notice）は出していない。画面の panel は警告を出すが、詳細画面への結線は A9。
4. `approval.decide`・`inbox.answer` は分類に入れていない（既存の basis と `human_required` の門のまま）。
5. TS（`project_controller.ts`）は snapshot の `authority` を読まない。起票の可否は Rust の門が決め、TS の proposal を置き換える。
6. `docs/api/v1/api.md` の registry の件数（143 行・ALLOWED 107・EXCLUDED 36）は A1 以前の数のまま。試験は件数の文を読まない。
7. 統括 CoS の run は autonomy の外（I13）なので、統括 CoS の操作には許可の門が当たらない（既存の gate のまま）。
8. snapshot の `authority.grants`（`crates/task-ops/src/project_snapshot.rs` の `authority_section`）は、取り下げた Outcome の許可も有効として載せる。今は TS が読まず（未解決 5）、
   起票の可否は Rust の門が `unknown_scope` で断るので、許可は広がらない。WU roadmap-scope の許可 path に `project_snapshot.rs` が無いので直していない。TS が読むようになる前に外す。
9. A7 と関係の無い不安定な試験が 1 件ある。`celeris::script_generation_e2e` の `script_generation_e2e_switch_error_rollback_restart` が、WU roadmap-scope の check で 1 回だけ
   `crates/celeris/tests/script_generation_e2e.rs:800`（`in_flight` が 1 でなく 2）で落ちた。再実行は通り、単独 6 回と `test-affected` 1 回はどれも passed で、失敗は再現していない。
   コードを読んだ原因の推定: `cos_digest_pass`（`crates/task-dispatch/src/dispatcher/cos_chat/digest.rs`）は `digest_due` を空の走査で初めて下ろすので、digest を書いた次の tick でも TS の pass が走る。
   試験の `stage_switch_to_b` は `in_flight == 0` を 1 回見ただけで pass を始めるので、その間に次の tick の pass が入りうる。「この段で新しい pass は来ない」という試験の注記もこの点で誤り。
   A7 はこの試験と digest を変えていない。WU の許可 path の外なので直していない。
