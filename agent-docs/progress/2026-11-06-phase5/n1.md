## fix-build-cache-adopt: `run_start_adopts_a_finished_target_that_predates_the_checkout` の失敗（試験の前提のずれ）
- 症状: attempt 1 の review の `test-affected` で `build_cache.rs:826` の `adopted_from` が `None`（期待は
  `Some("release-0123456789ab")`）。単独の `cargo nextest run -p task-dispatch -E 'test(run_start_adopts_a_finished_target_that_predates_the_checkout)'`
  では通る（1 passed、0.5 秒）。
- 原因: **試験の前提のずれ**（製品 code の不具合ではない）。試験の dispatcher は `min_free_disk_mb = 5120` のままで、tick の
  scratch GC（`plan_gc`）は tempdir の filesystem の実の空き（statvfs）を見る。空きが 5〜10 GiB だと pressure が `LowDisk` になり、
  seed（使用中の repo の最新の P3。この試験の `release-0123456789ab`）も回収に選ばれ、adopt の候補から外れる。空きが 5 GiB 未満なら
  disk guard が dispatch を止め、10 GiB 以上なら通る。LowDisk で seed を回収するのは ADR-0075 D1/D2 どおりの挙動。
  mtime・候補・距離・P0/P3 の分類の順、main の scratch の変更は原因ではなかった（分類と候補は変えずに空きの条件だけで再現した）。
- 根拠（決定的な再現）: 試験に一時的に `d.config.min_free_disk_mb = fs_stats(scratch_dir).free × 3/4 ÷ MiB`（空きが min と 2×min
  の間になる値）を足すと単独でも同じ assert（`left: None`、`right: Some("release-0123456789ab")`）で落ちた。`u64::MAX` にすると
  disk guard で task が終わらず別の場所（`tests/mod.rs:317` の待ち）で落ちた。この run の時点で `/tmp`（tmpfs）の空きは 11 GiB で、
  閾値の 10 GiB に近い。review の check がどの filesystem の tempdir で走ったかは未確認。
- 直し方: 試験の共通の helper `scratch_on`（`crates/task-dispatch/src/dispatcher/tests/mod.rs`）で `min_free_disk_mb = 0` にし、
  scratch の試験を host の空きから切り離した（空きを見る試験 `low_disk_runs_emergency_gc_before_pausing_dispatch` などは helper の
  後で明示的に上書きしているので変わらない）。再現試験 `low_disk_reclaims_the_warm_seed_that_would_be_adopted`
  （`crates/task-worker/src/scratch/tests.rs`）は `fs_free_bytes` を注入して、空き 20 GiB では seed が残り、8 GiB（min 5 GiB）では
  LowDisk で seed が選ばれ、min 0 では残ることを固定する。製品 code は変えていない。設計判断は無いので ADR は足していない。
- 検査は下の「検査」節（提出時の HEAD で再実行）。
