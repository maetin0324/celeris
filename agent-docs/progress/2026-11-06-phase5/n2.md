## 5. 72 時間の要否
判断: **今は 72 時間を走らせない**。runbook の規則（24 時間で傾きが数値を超えたら 72 時間の承認を求める）にはこの途中の値で当たるが、
次の理由で、先に 24 時間の完了と tick の修正を待つ。
- 今の負荷では tick の所要時間が 1 時間に約 8 秒ずつ伸び、処理が投入に追いつかない。72 時間走らせても、この backlog の増え方を長く測るだけで、
  memory の定常の傾きは測れない。
- shadow・enabled の off との差（+15 MB/時）は 9 時間ですでに見えている。72 時間は差の有無を決めるのに要らない。

72 時間を行う条件と承認:
1. 今の 24 時間を完了させ、回収・集計する（上の 3.）。
2. `tick_cos_chat_launch` の伸び（下の提案 1）を直した build で、24 時間を走らせ直す。これには新しい承認の file が要る
   （今の承認は 2026-11-07T00:00Z で切れ、1 回分の 86,400 秒）。
3. 直した build の 24 時間でも shadow・enabled の傾きが off + 0.5 MB/時 を超えたときだけ、72 時間を求める。承認は人が書く file で、
   `python3 -I scripts/dev/daemon-soak/daemon_soak.py plan --hours 72` の雛形（`approved_by` human:<名前>、`scope` non-production、
   `max_secs` 259,200、4 条件、`expires_at`、`host`）。72 時間の推奨 `--max-db-mb` は plan では 35,889 だが、実測の DB は 9 時間で 0.4 GB 以下で、
   plan の見積もり（26 分の実測からの比例）は大きすぎる。実行は operator が worker の外で行う（worker の中では 1 時間を超える run は門が断る）。
