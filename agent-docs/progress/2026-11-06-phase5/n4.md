# N4 10,000 件 blocked Task の dispatch と起動時 tick

before/after を同じ時間帯に並べて 16 cell を測り直した（対の計測）。10,000 件の dispatch p50 は off 514 ms・shadow 707.5 ms で、1 秒目標は満たした。500 ms 目標は満たしていない。
restart 最初の tick の中央値は、10,000 件で off 5.549 → 3.490 秒、shadow 6.169 → 3.149 秒に短縮した。
前回の 600 件・2,000 件の退行（93→269・205→495 ms）は、before と after を別の時刻に測ったことによる host 負荷の差だった。同じ時間帯に並べると、後/前 の比は 0.75〜1.02 になった。

- 実行: 各 round で 4 本（before/after × off/shadow）を同時に起動した（[run-round.sh](n4/paired/run-round.sh)）。各 process の条件は `TICK_SCALE_TICKS=5 TICK_SCALE_DISPATCHES=5 CELERIS_SCRIPT_REQUIRE_BUNDLE=1`、fixture は SQL clone、restart 後に settle してから dispatch を測る。off は lane_rules=rust、shadow は lane_rules=compare（本物の V8）。LLM は呼ばない。

## 提案
- 500 ms を目指すなら、新しい root の event 取り込みで Task 全件を読むのをやめる。触れた Task と、その root・子・依存元・承認・下書きだけを読む範囲 query が要る。複合項目が使う関係を欠かさない設計を先に ADR で決める。
- 性能の比較は、同じ時間帯に before/after を並べる対の計測を標準にする（`summarize_paired.py` の形）。別の時刻の計測では、この host の負荷の揺れが版の差より大きい。
