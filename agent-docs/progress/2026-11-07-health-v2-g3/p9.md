## 実装前 brief
1. 根本原因: `cascade_after_transition_tx` は `from.is_terminal()` なら何もしないので、依存先が終端から戻っても `dependency_failed` の cancel が残る。症状は後続が cancelled のまま止まること。
2. 責務 owner: `crates/task-core/src/store/transition.rs` の `cascade_after_transition_tx`（依存の cascade の唯一の場所）。
3. 既存の再利用先: `apply_transition_tx`（遷移と event の追記と cascade の再帰）、`dependents_of_tx`、`last_transitioned_reason_tx`（`last_transitioned_tx` に置き換え）、`retry_task_tx` の「cancelled かつ最後の遷移が `dependency_failed`」の判定（`transition::cancelled_by_dependency` に抜き出して共有した）。
4. 選択肢: (a) reopen の API（`task_ops::comment::reopen`）で戻す、(b) cascade で戻す。(b) を採った。reopen・rereview のどの入口でも同じ transaction で戻り、依存の cascade が 1 か所に残る（B0 の consolidate_into_owner）。
5. 新しい状態・分岐: `Trigger::DependencyReopened { draft }` と cascade の枝 1 つ。fallback・切替 flag は無し。
6. 撤去対象: retry の判定の式（共有の述語に置き換えた）、`non_terminal_dependents_tx`（`dependents_of_tx` に統合）、`last_transitioned_reason_tx`（`last_transitioned_tx` に置き換え）。
7. 不変条件と試験: 下の 5 件。events は追記だけで、cancel の event を変えない。人・CoS の cancel と連鎖の中止は戻さない。

## 試験（守る不変条件と、既存の試験で検出できない理由）
既存の `dependency_failure_cancels_dependents_transitively` は cancel の向きだけを見ており、reopen の後に後続が cancelled のまま残る不具合を検出できない。
- `dependency_reopen_restores_cancelled_dependents_transitively`: A の reopen で B と、B に依存する C が ready に戻る。cancel までの event は同じで、`Transitioned{cancelled→ready, dependency_reopened}` が 1 件だけ足される。戻った後続は A の done を待つ（`ready_tasks` に出ない）。
- `dependency_reopen_keeps_dependent_while_another_dependency_failed`: ほかの依存先 E が failed の間は戻らず、E の reopen で戻る。
- `dependency_reopen_keeps_manually_cancelled_dependent`: 手での cancel（`cancel`）と木の親の中止（`parent_cancelled`）は戻らない。
- `dependency_reopen_returns_draft_dependent_to_draft`: cancel の前が draft なら draft に戻る（ready にしない）。
- `dependency_reopen_on_rereview_and_cancels_again_on_failure`: rereview（failed → reviewing）でも戻り、再判定の不合格で再び `dependency_failed` になる（理由の列は追記だけ）。

## 目的文・ADR との違い
- 戻す先: ADR D7.1 は「Cancelled → Ready」。cancel の前が draft の後続は draft に戻した。人が受け入れていない task を reopen だけで ready にしないため。
- 人の回答の「pending」は、依存先の done を待つ ready として実装した（Celeris の状態に pending は無い）。

## 提案
- 範囲の拡張: 範囲 check に `^crates/task-api/src/inbox_notifications\.rs$` と `^web/features/inbox/` を足す（新しい受信箱の種類の網羅の match と `KIND_LABELS`・`INBOX_KINDS`・`NATIVE_KINDS`・`inbox-model.test.ts`）。新しい event を足す案なら `^crates/task-api/src/query\.rs$` も要る。
- 新しい event を足さない案: 受信箱は DB に行を持たない派生の一覧なので、「最後の遷移が `dependency_reopened` で終端でない task」を `task_ops::inbox` の attention で拾えば、項目の正本は既存の `Transitioned` になる。依存先は task の `depends_on` から出せる。この案なら `query.rs` は変えない。
- 受信箱の項目の設計案（新しい event を足す場合）: reopen した task に event `DependentsReopened { restored: [task id], kept: [{task, reason}] }` を同じ transaction で追記し（restored も kept も空なら書かない）、`task_ops::inbox` の attention と新しい受信箱の種類 `dependents_reopened` で出す。項目は戻した後続ごとに task id と依存先を書き、native の操作は後続の `POST /api/v1/tasks/{id}/cancel`。戻した後続が動き出す（最後の遷移が `dependency_reopened` でなくなる）か終端になれば消える。
