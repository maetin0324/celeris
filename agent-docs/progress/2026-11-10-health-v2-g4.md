## ADR の期待を契約に合わせた訂正
- ADR の初版は、`dup.*` が fail 級（exit 1）になり、`deps.violation` が層の宣言なしでも動く前提で書いていた。契約 [ADR 2026-11-07 repo health の契約](../adr/2026-11-07-repo-health-contract.md) では、`dup.*` は候補（candidate=true・severity warning 以下）で verdict に影響せず、review に渡る材料になる。`deps.violation` は層の宣言が無ければ `not_applicable`。py-detect の v1 の試験はこの食い違いで 12 件落ちた。
- 検査器は契約どおりに動いているので、検査器は変えず ADR と試験を直した（ADR の「付記（2026-11-10、unit py-detect）」）。dup-contract・dup-state の期待は「候補が 1 件、exit 0・verdict pass、final review の材料に入る」。fail 級の土台（policy の弱化 5 種・history-smuggle・(e)(g)(h) の Fail と repair、class `health:deps.violation`）は、fixture の base の profile が層を宣言した dep-inversion に移した。
- 実装とのその他の食い違い（variant の追加、flag の実名、rust の `deps.cycle`、measure の回数と file 名など）は ADR の「付記（2026-11-11、unit record）」。

## 解決した欠け G4-S1
- 欠け: `Check::Reviewer` のある task で決定的な条件が落ちると、review は reviewer run を起こさず reviewer の項目を「not evaluated: a deterministic check failed」の不合格にする。`Dispatcher::try_review_repair` がこの項目も分類に入れたので、health の Fail も fmt の不合格も Substantive になり、repair に回らず `review_fail` になった。rs-stale が見つけた。
- 直し: unit fix-s1。`crates/task-dispatch/src/dispatcher/review_verdict.rs` の `try_review_repair` が、決定的な不合格があるとき reason が `review::REVIEWER_NOT_EVALUATED_REASON`（`crates/task-dispatch/src/review.rs`）の項目を分類から外す。[ADR-0072](../adr/0072-task-execution-decomposition.md) の付記 G4-S1。`task_core::classify_review_failure` は変えていない。
- 試験: fix-s1 の `review_repair_not_evaluated_reviewer_does_not_block_a_health_repair`・`review_repair_not_evaluated_reviewer_does_not_block_a_format_repair`・`review_repair_not_evaluated_only_skips_the_not_evaluated_reason`。rs-stale の `health_generic_reviewer_reuse_health_fail_routes_to_repair` は `should_panic` を外して合格する（class `health:deps.violation` だけの review の repair の後に done）。

## 未解決の欠け
### G4-R1: `[review]` 節の無い repo で候補の finding が final review の材料に入らない
- 再現: `python3 -I scripts/tests/repo_health_fixtures.py build ts dup-contract <dest>`（ts の dup-state、rust の dup-contract・dup-state も同じ）。task に `Check::Reviewer` を足して final review を流す。
- 期待（G4 の ADR (3) の `review_input_`）: `HealthReviewInputBuilt` の `input.findings.new` に `dup.contract`（`dup.state`）が path 付きで 1 件入る。
- 実際: `HealthReviewInputBuilt` は 0 件で、`HealthReviewInputSkipped` の reason は `health_review::input::POLICY_ABSENT`（base の profile に `[review]` が無い）。候補の finding は report にはあり、health は Pass。
- 食い違いの元: [ADR 2026-11-07 health-review-integration](../adr/2026-11-07-health-review-integration.md) の D4.4 は、review 方針が `absent` の repo で `ReviewRequest.health = None` にすると定める。G4 の ADR は、方針の無い汎用 repo でも候補が reviewer に届くと期待した。fixture の profile も組み込み generic も `[review]` を持たないので、Celeris 以外の多くの repo で同じことが起きる。
- 試験: `health_generic_review_input_{ts,rust}_{dup_contract,dup_state}_reaches_reviewer` の 4 試験は、期待を弱めず `should_panic(expected = "no HealthReviewInputBuilt for the candidate")` で残した。直ると panic しなくなって落ちるので、外し忘れは分かる。

- 2 試験とも `@unittest.expectedFailure`。人の決定 checker-gaps は a（G4 では直さず、G4 が main に入った後に policy だけの別 task で直す）。

## 段 hardening の統合を止めた試験
### deflake-ws（直した）
- 症状: 統合の test-affected で `dispatcher::tests::git_workspace::review_records_each_repositories_own_definition_and_worktree_results` が `each repository must have its own evidence` で落ちた。
- 原因: 試験は `run_until_idle(&mut d, 60)` で待つ。この関数は 60 tick で idle にならなくても黙って戻る。review の必須検査は tick の外の task で走るので、負荷で遅いと `RequiredChecksEvaluated` が書かれる前に試験が event を読む。本体の review の経路は正しく動いている。
- 直し: 試験の file に helper `run_until_terminal_and`・`run_until_terminal` を置き、`mod.rs` の `run_until_state`（ADR-0125 の出来事待ち、60 秒の保険）で「task が終端の状態」と追加の条件を待つ。review の必須検査の結果を読む 9 試験をこの待ちに直した。期待の assert は消していない。
- 確かめ方: check の command に一時的に `sleep 3` を入れて負荷なしで再現した。修正前は同じ panic で exit 100、修正後は exit 0（[deflake-ws.md](2026-11-10-health-v2-g4/deflake-ws.md)）。

### `celeris-campaign::dagbench_process` の `recovery_notice_continuation`（G4 から外した）
- 統合の test-affected で、この試験が 600 秒の TIMEOUT になった。unit deflake-notice が 2 回調べたが、hang に至る順序を特定できなかった。疑った順序（c1 が wait を保存する前に止まり c2 が 2 node を再実行する）は 1 回の実行で現れて合格し、c1 が wait を保存した場合も合格した。負荷による遅さの見込みも残る（未確認）。直す前に落ちる試験を書けないので、修正も `notice_stall_` の試験も入れていない。
- 計画 v6 で deflake-notice を G4 から外した（unit は superseded）。理由: G4 の branch は `crates/campaign` を変えておらず、この試験の原因の調査は G4 の目的の外にある。調査の記録は [deflake-notice.md](2026-11-10-health-v2-g4/deflake-notice.md)（status abandoned）。
- 段 hardening の統合は、v6 で deflake-ws を入れた後にやり直して完了した（途中の repair-hardening-1・2 は repo を変えていない）。

## measure の要点
3 kind × 16 variant（64 repo）に本物の検査器を各 5 回当てた（計 336 回。5 回の結果はすべての repo で一致）。詳しくは [measure.md](2026-11-10-health-v2-g4/measure.md)。

| 項目 | 結果 |
|---|---|
| 候補の検出（dup.*） | 8/8（100%） |
| fail 級の検出（deps.violation・policy.changed・history-smuggle） | 48/48（100%） |
