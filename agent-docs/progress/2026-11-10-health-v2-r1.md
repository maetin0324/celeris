## 提案
1. 負荷で落ちる試験を決定的にする別 task（R1 の範囲外）を起こす。対象は task-worker の `browser::launcher_run::tests::launcher_login` の 4 件と celeris-campaign の `k4_cells_validity::real_k4_archive_grades_thirty_of_thirty_two`。前者は login の期限（15 秒・5 秒）を実時間で待つので、時計の差し替え（`tokio::time::pause`）か試験用の期限の注入で、負荷に依らず同じ結果にする。後者は 600 秒の timeout に頼らず、採点の対象を縮めるか、待ちを出来事待ちにする（`agent-docs/guides/testing.md`）。task-worker を変える task の統合で同じ失敗が出続けるので、R6 より先に入れると R6 の統合が通りやすい。
2. R6（task 01M6TYVJT7EJ6WWHEF0EBH3JPS）への引き継ぎ（ADR (5)）。`langmem.rs`・`local_deep_research.rs`・`paperqa.rs` の監視 loop は 5 adapter と同じ形（`start`・`last_activity`・`min(..)` の待ち・`read_line_limited`・`kill_now`/`reap_after_terminal`）で、`adapter::deadline_terminal` に寄せられる。langmem は `[adapters.langmem].idle_timeout_secs` で idle を縮めるが、`deadline_terminal` は `idle_timeout` を値で受けるのでそのまま渡せる。ただし 3 本は wall clock の超過を `Error{retryable: true, "wall clock exceeded"}` にしていて、5 adapter の `BudgetExhausted{WallClock}` と違う。dispatcher は文言の安全網（`task_core::is_budget_outcome`・`classify_budget_kind_from_text`）で予算切れとして拾うので task の遷移は同じだが、`runs/<run_id>/result.json` の `WorkerMessage` と `WorkerFinished` の構造化した欄が違う。`deadline_terminal` に寄せると分類が変わるので、R6 で分類を決め、研究 harness の run が `Yielded`/continuation の経路に乗らないことを試験で固定してから寄せる。`subprocess::prepare_run`・`finish_run`・`adapter::spawn_capture_stderr` も 3 本の写しに使える。
3. R6 で決める: dispatcher 側の `misplaced_report` の呼び出し（`dispatcher/worker_task.rs`）は、5 adapter が `read_result_file` で自分で呼ぶようになったので、残る役目は `Err(AdapterError::Other)` の経路と R6 の 3 adapter・`fake`・`run_subprocess` の覆いだけ。R6 が 3 adapter に `read_result_file` を通した後、消すか `Err` の経路だけに縮めるかを決める（ADR (5) 4）。
4. 済み（unit wait-line）: `result_report_tests.rs` の `RunContext` の組み立てを `RunContext { cos_chat: Some(Default::default()), ..Default::default() }` にした（未解決 3）。
