## 結論

- 通知・観測しか要らない sink（`ReviewerSink`・`ChatRunSink`・`PrintSink`・`NullSink`）と harness に渡す `BrowserSink` は、型の上で Browser の認可・制御・secret の能力を持たなくなった。能力は `BrowserAuthority`（6 method、secret と承認）と `BrowserControl`（4 method）に分かれ、本番の実装者は `StoreSink` だけで、`run_worker` が browser の run にだけ渡す。
- browser の run に能力が無ければ、policy・substrate・harness より前に `browser capability not injected` で拒否する。既定 `true` の `browser_saved_credential_valid` は消えた。
- `WorkerAdapter` の with_* 5 つは `configure(&AdapterSettings)` 1 つになり、写し（非試験 31・試験 31）と呼び出し側の重複条件（`prepare_run_adapter` の match 4 つ、env だけの判定 5 か所）が消えた。移行のための旧い経路は残していない（期限・撤去条件の要るものは無い）。
- 途中で 2 つの問題を直した。settings 段の統合で落ちた launcher login 試験（原因は credentiald の固定 5 秒の待ち。別 ADR [2026-11-11-credentiald-passed-stream-wait](../adr/2026-11-11-credentiald-passed-stream-wait.md)）と、同じ段の health の指摘 `size.responsibility-growth`（dispatcher の module の行の増加）である。
- 全体 suite・userns・実 browser の試験は実行していない。release gate（`scripts/selfdeploy/release.sh`）の担当である。

## settings 段の統合の失敗と launcher-login-fix

- 段 settings の統合の検査で、`browser_launcher_run_tests.rs` の launcher login 試験が `Recorded(Err("launcher_authenticate_rejected"))` で落ちた（統合の nextest 5867 件中の 1 件、host は高負荷。単独では 3.48 秒で合格）。
- 原因: daemon は auth section を開いてから credentiald の `injection.sock` に接続し、その FD を launcher に渡す。launcher が注入の要求を書くのは login 頁の password 欄が出た後になる。credentiald は接続の最初の要求を `IO_TIMEOUT`（5 秒）しか待たず、5 秒を超えると要求を読む前に拒否した。接続の順は 2026-10-09、5 秒の待ちは 2026-09-30 からあり、browser-port・adapter-settings の退行ではない。
- 直し方（原因の owner の credentiald）: 最初の要求の待ちを、`IO_TIMEOUT` ごとに見直す出来事待ちにした。待ち続けるのは peer が開いた auth section を持つ登録済み controller の間だけで、保険は `PASSED_STREAM_BACKSTOP` 120 秒（launcher の action の期限に揃えた）。auth section を持たない peer は従来どおり 5 秒で拒否する。
- 再現は CPU 負荷を使わず、fixture の IdP の `POST /password` を `IO_TIMEOUT` + 1 秒保留する gate（出来事待ち）で行い、直す前は FAIL、直した後は PASS だった。

## inject-wait の結果

- 決定 inject-accept の回答は a（最初の要求の待ちだけを接続ごとに並行にし、照合・lease の消費・注入は 1 本の thread で直列、待てる接続は 8 まで）。operator は計画 v5 の承認で「回答 a（note の条件を含む）のとおり」と答えた。
- launcher-login-fix の後、auth section を開いた接続は最初の要求を最長 120 秒待つので、受付が 1 接続ずつのままだと他の session の注入が止まる（修正前は最長 5 秒）。inject-wait は credentiald の受付を `accept_injection`（`ipc.rs`）に置き換え、旧い `serve_injection` を消した。要求の body は `Zeroizing` のまま照合 thread へ move する。
- 決定は ADR [2026-11-11-credentiald-passed-stream-wait](../adr/2026-11-11-credentiald-passed-stream-wait.md)（ADR-0109 D1 の「読み取り期限 5 秒」を改める。D1 期限、D2 auth section への結び付け、D3 保険 120 秒、D4 受付の並行、D5 上限 8）に書いた。R2 の ADR の付記（食い違い 13）は、launcher-login-fix が credentiald の待ちを変えたことと、この ADR を指す。
- 残る影響: 照合が直列なので、前の login の controller の CDP mux が sink に答えないと、後の login は launcher の 5 秒を超えて `Rejected` になり得る（credential は漏れない）。下の「提案」に書く。

## 提案

- credentiald の照合が直列なので、前の login の controller の CDP mux が sink に答えないと、後の login は launcher の 5 秒を超えて `Rejected` になり得る（[ADR 2026-11-11](../adr/2026-11-11-credentiald-passed-stream-wait.md) の「直列の受付の影響」）。同時の credential login が増えたら、sink の応答待ちを照合の直列から外すかを別の task で決める。
- `launch_notice_tests.rs` の fixture に、試験専用の書き込める `CODEX_HOME` を明示的に渡す修正を owner の別 task で行う（browser-port の記録）。
- `review_records_each_repositories_own_definition_and_worktree_results` の負荷下の失敗は、tick 数の上限ではなく出来事待ちにする（G4 の deflake-ws が扱う）。post-login の `target_changed` の時間依存も owner の試験 fixture で決定的に再現して直す（browser-port の記録）。
- repair WU の範囲外差分の検査は、段の統合の health の指摘なら段の write_set（または operator が認めた範囲）から作る（repair-settings-2 の記録）。
