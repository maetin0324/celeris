## 提案
1. browser login と credentiald の login の待ちを ADR-0125 の出来事待ちに直す。owner は task-worker の browser login（`browser_post_login_tests.rs`・`browser_launcher_run_tests.rs` が試す経路）と celeris-credentiald の injection の待ちで、固定の秒で待つ所を「接続・要求・状態の変化」の出来事と長い保険の上限に替える（login-flake.md の §5）。
2. scratch の seed の写しで、build script の出力（`target/<profile>/build/*/output`）の絶対 path が古い世代を指す。`crates/task-worker/src/scratch` の `seed_target` が写した後に output の seed 世代の path を owner の target の path へ書き換えるか、退避の GC が写し先に参照の残る世代を消さないようにする。それまでは `v8-target-check.sh` を段の check の先頭に置くと、同じ原因の失敗の log が原因を名指す（v8-guard.md）。
3. WU の health（task-dispatch の `work_unit_health`）に、段の統合の `phase_health_base` と同じ base の規則を入れる。今は WU で main を merge すると、main 側の policy の変更が WU の差に入り `policy.changed` になる（resync-g4 が外れた原因）。
4. test-affected の対象が広い task（task-worker・task-core を変えると workspace のほぼ全 crate と web が入る）の WU・review の check の上限（600 秒、再実行 1200 秒）を見直す。R5 の段の統合の test-affected は 858〜1375 秒かかり、celeris の 1200 秒の時間切れが 1 回あった。上限を対象の広さで決めるか、統合の check と review の check で同じ test-affected を二重に走らせない形を検討する。
5. r6 の 55 target（task-api 36・celeris 12・celerisctl 7）は、R6 で `docs/architecture-map.md` の行の path を束の path に直す変更と一緒に束ねる。`classify.py` と `inventory.json` の束の案（capability group と fixture の鍵）はそのまま使える。
6. file 名に数字を持つ target（workspace で 44 件、4 crate で 22 件）を動かせるよう、R6 以降の write set の正規表現を `tests/[a-z0-9_/]+\.rs` にする。B0 の slices.json の変更なので、計画の段で人が決める。
7. test-affected の作り直しで直せなかった分:
   - doc test は対象に依らず `cargo test --doc --workspace` を走らせ 17〜25 秒かかる。doc test を持つ crate（task-core・celeris-script・task-worker）の逆依存に入る時だけ走らせる案を ADR で検討する（measure-build.md の提案 2）。
   - `--workspace` の features の版が target に無い初回は、対象外の crate の test binary も build・link する。scratch の seed が `--workspace` の版を持つかは未確認。
   - stable の cargo が `resolver.feature-unification = "workspace"` を読むようになったら、filter を `-p` に戻して `CARGO_RESOLVER_FEATURE_UNIFICATION=workspace` に替える（ADR D6-6。撤去の条件は ADR に書いてある）。
8. 計測の台本: run でも base と HEAD を同じ時間帯に交互に走らせる（celerisctl は load の比 1.901 で秒が 2〜3 倍になり、比べる値が無かった）。run1 の前に `celeris-campaign` の binary も build する。nextest の `SKIPPED (` を数えて本体まで走った件数を記録する（measure-run.md）。
