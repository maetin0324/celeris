# KB の run ごとの利用計測と検索入口の改善

実装と必須検査は完了。検査の結果は「証拠」に書く。

全体の完了日: 2026-11-12。

## 決定（ADR）

- `agent-docs/adr/2026-11-11-worker-knowledge-entry.md`: worker の prompt の索引の列挙（最大 200 件、約 57 KB）をやめ、短い検索の入口（search → get → record の手順）にする。関連ページの自動挿入はしない。
- `agent-docs/adr/2026-11-12-knowledge-usage-per-run.md`: KB の操作を入口と API の受け側で run ごとに数える（D1〜D3）、report（D4）、curation は同じ話題の新規を拒否して更新・統合を先に選ばせる（D5）。

## 実装前 brief

1. 根本原因: 読み取りの数は harness の log からしか取れず（chat_events の要約の 84% が `[redacted]`）、worker の prompt には関連度の無い索引が入り、curation の検査は同じ話題の新規ページを通していた（統合 2 ／ 新規 450）。
2. 責務 owner: 入口 `celerisctl knowledge`（`crates/celerisctl/src/commands/knowledge.rs`）、台帳 `task_core::knowledge::usage`、worker run の用意と読み取り `task_dispatch::knowledge_usage`、CoS run の受け側 `task_api::cos::knowledge_use`、curation の検査 `task_ops::knowledge_curation::validate`、report `task_ops::knowledge_usage`。
3. 再利用: followups の env と run 前の置き直し（ADR-0098）、`RunMetrics`（`WorkerFinished.metrics` → `runs.metrics_json`）、CoS run credential（`CosCaller`）、`work_unit_checkpoint_site`（WU の artifacts）。
4. 選択: worker run は台帳 file（run の中の CLI が書き、daemon が run 後に読む）、CoS run は API の受け側（credential が run を決める）。CoS も台帳にする案は、dispatcher の module（repo health の閾値超え）に配線の行を足すので採らない。
5. 新しい状態: `RunMetrics.knowledge`（任意欄）、`chat_runs.knowledge_use_json`（migration 0125。版 124 は別 branch のため予約、123 は main の authority の migration）、route `POST /api/v1/cos/knowledge-use`、CLI `celerisctl knowledge usage`。fallback・切替 flag は無し。
6. 撤去: worker の索引の列挙と上限定数、「候補は人が確認してから正本に入る」の説明（phase 1）。
7. 不変条件と試験: 下の「試験」。

## 試験（守る不変条件）

- `task-core knowledge::usage::tests`: 台帳の行を op ごとに足し、壊れた行を数えない。
- `celerisctl tests/knowledge_usage.rs`: binary の入口で search・get・record を 1 回ずつ数え（失敗も数える）、env が無ければ書かない。
- `task-dispatch knowledge_usage::tests` と `dispatcher::tests::knowledge_usage`: run の前に前の run の台帳を置き直し、run の中の回数が `WorkerFinished.metrics.knowledge` に入る。
- `task-api tests/cos_knowledge_use.rs`: credential の run の `chat_runs.knowledge_use_json` に数え、body の run id・人の token を受けず、NULL の run（計測前）を数えない。CoS が常設の文脈の案内どおり `GET /knowledge/tree`・`GET /knowledge/page`・operation `knowledge.record` を呼ぶと、受け側が同じ run に search・get・record を数える（404 は失敗として数える）。人の token の同じ呼び出しは数えない。`POST /cos/knowledge-use` の `record` は 422（二重に数えない）。
- `task-ops knowledge_usage::tests`: 計測した run だけを分母に agent・案件ごとの読み取り率、curation ごとの統合の比率、CoS の行。
- `task-ops knowledge_curation::tests::new_page_on_an_existing_topic_is_rejected_and_update_or_merge_passes`: 同じ置き場の同じ話題の新規は拒否、fix と merge は通る。

## attempt 2（review の不合格の直し）

review（attempt 1）の不合格は 2 点だった。

1. CoS の常設の文脈が案内する `GET /api/v1/knowledge/tree?q=`・`GET /api/v1/knowledge/page?path=` と operation `knowledge.record` を、受け側で数えていなかった。直し: `task_api::cos::knowledge_use::note` を足し、tree（search）・page（get）・`create_operation` の `knowledge.record`（record）が CoS run の credential の呼び出しを数える。CoS の `celerisctl knowledge record` は operation を通るので CLI では数えない。`POST /cos/knowledge-use` は API を通らない `celerisctl knowledge search|get` だけに使い、`record` は 422 にした。
2. ADR D3 は reviewer・planner も計測すると書いていたが、実装は worker の run だけだった。直し: ADR D3 を実装に合わせ、計測するのは role が worker の run で、reviewer・planner・設計 review の run は計測しない（`None`。理由と、計測するときに決めることを ADR に書いた）。
3. health の removal_missing（advisory）: `celerisctl knowledge record` の出力 2 か所・`--path` の help、`docs/ops/cos-chat.md`、知識抽出の prompt（`task_core::knowledge`）、`InboxOp::Append` の説明に残っていた「人が確認してから正本に入る」を、日次整理の検証の後に正本に入る説明に直した。
4. architecture-map に「KB の利用の計測」の行を足した（`scripts/dev/check-architecture-map.py` exit 0）。
