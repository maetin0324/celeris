## 結論

**完了。** (a)・(b) を ADR のとおり実装し、提出時の HEAD で受け入れ条件の検査が全部 exit 0 だった。

- **(a) 根本原因と直した欄。** `scripts/dev/test-parallel.sh` の集計の python は nextest の Summary 行を
  `re.findall(r"(\d+) ([a-z ]+?)(?:,|$)", …)` で割っていた。本物の nextest は `8525 passed (3 slow), 22 skipped` と注記を付けるので
  `passed` の組が取れず、nextest の通過数は 0 になっていた。そのため gate.json の `cargo_test.passed` は doc test の通過数だけ、
  `ignored` は nextest の skipped と doc test の ignored の和になっていた（本番の 4 release で `passed` 3・`ignored` 24）。
  WorkUnit `counts` が括弧の注記を外してから数えるように直し、`cargo_test` に `nextest_passed`・`nextest_skipped`・`doc_passed`・
  `doc_ignored` の 4 欄を足した。`passed`・`failed`・`ignored` は今までどおり nextest と doc test の和。legacy の runner
  （`SD_GATE_TEST_RUNNER=cargo-test`）は内訳の欄を持たない（ADR D1）。
- **(b) 置き場と正本の規則。** WorkUnit `summary` が `scripts/selfdeploy/lib.sh` に `sd_release_record <gate|verify|promoted> <正本の path>` を
  置いた。release.sh（成功の gate 1 か所・失敗の gate 2 か所）・verify.sh（1 か所）・promote.sh（1 か所）が、正本の file を書いた後に
  `$SD_LOGS/release-records.jsonl`（本番は `paths.env` の `CELERIS_LOGS_DIR`＝`/local/celeris/state/logs`）へ 1 行の JSON を `>>` で追記する。
  この dir は release の掃除が触らない。release dir がある間は、その中の gate.json・verify.json・promoted.json が正本で、要約の log は
  書いた時点の写し。`crates/celeris/src` の releases.rs・delivery.rs・release_notes.rs も台本も、昇格・takeover・引き渡し・release notes の
  判断に要約の log を読まない（`unpromoted-release-no-takeover`）。食い違えば release dir の file を信じる。追記に失敗しても警告 1 行だけで、
  台本の結果は変わらない（ADR D2〜D4）。
