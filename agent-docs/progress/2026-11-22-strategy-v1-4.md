## 結論

- MCP 対応の外部 LLM（ChatGPT の RDC・custom remote MCP、Muse など）は、既存の MCP の registry・認証・client ごとの scope・`mcp_calls` の監査・流量制限の下で、
  同じ 3 道具を使う: `discussion_snapshot`・`discussion_evidence_search`（scope `discussion:read`）と `discussion_propose`（scope `discussion:propose`）。
  HTTP・`celerisctl mcp stdio`・`celerisctl mcp call`（RDC の `celeris-chat`）は同じ `rpc` の dispatch を通る。
- 外に出るのは、人（`Principal::Human`）が共有した message（revision と sha256 に固定）と、呼んだ client 自身の案だけ。既定は空。撤回・共有の後の編集・
  取り消し・期限切れ・confidential の文書・knowledge は出ない。秘密の形は共有の時に 422 で止め、出す時に `[masked]` にする。
- 外部 LLM の案は案件 thread の `author = mcp:<client_id>`・`discussion_mode: discuss` の未承認の draft で、人の発言にも承認にもならない。
  envelope の R10・R13 は文書の自己申告の `approval` を読まなくなり、`human:` の主体が答えた決定の記録と人の共有の記録からだけ導く。
- MCP 非対応の経路として、人の token だけが呼べる REST の 4 route（共有・取り消し・書き出し・取り込み）を足した。書き出しは JSON と Markdown。
  ChatGPT のどのプランでも人の貼り付けで使える。custom remote MCP は optional。
- 人の決定 `ext-client-scope` の答え b に従い、MCP の `decision_answer`・`task_plan_gate` を `tasks:interact` から `tasks:decide` に移した。
  ChatGPT の RDC の client `chatgpt-rdc-2` の推奨 scope では、人の決定・計画・task の承認に答えられない。`db:read`・`api:read` は人が残すと決めた。
- RDC の経路 `scripts/rdc/celeris-chat` → `celerisctl mcp call` → MCP を、実 binary と試験の MCP server で通し、`thread_id`・`project_id`・出典で
  会話が続くことを確かめた。本物の RDC home-dev・ChatGPT・Muse での確認は未確認（人が昇格の後に行う。下の「本番への移行」）。
- 計画 v4: 最終 review が、Markdown の取り込みの front matter の flow 値を深さの上限なしに再帰で読む欠陥（`[` を 5,000 段入れた 10 KB の文書で
  2 MiB の stack が溢れ、daemon が abort する）を見つけた。depth-guard が入れ子を 16 段（`FLOW_DEPTH_MAX`）までにし、17 段以上を 422 `exchange_invalid` で
  拒否するように直した（下の「計画 v4 の再計画」）。
- 新しい DB 表・migration・Manager・trait・状態機械・Agent サービスは足していない。production の行は +2,796（すべて Rust）の純増で、理由は下の LoC の節。
- 親の目的への寄与で確認済みなのは、改善 B（外部の議論を出典・hash 付きで共有する入口）と安全の不変条件（外部 LLM の発言を承認と取り違えない）だけ。
  改善 A・C・D と observability は推定か未確認。
- 本番昇格・publish・外部公開の MCP の配置はしていない。`scripts/selfdeploy/` は変えていない。

### 最終 review（reviewer run 01M8237ECGA6QER1CZKWEXNJCQ）の advisory 4 件（計画 v4 の範囲の外）

   WU の範囲の外」を理由にしたが、task-core は既に `schemars` に依存している（`crates/task-core/Cargo.toml`）。直し方: domain の 4 型に `JsonSchema` を
   derive し、`ApiV1Schema` がそれを直接登録して、`exchange_wire` の写しの 4 型と `From` を消す（`exchange_wire` には応答の型だけを残す）。生成物
