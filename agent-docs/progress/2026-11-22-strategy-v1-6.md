## 提案

1. 第二ゲートの戦略の再評価（人に質問した。決まるまで integrate-close と子 7 は進まない）:
   - 案 1（推奨）: 条件付き合格にして子 7 へ進む。独立評価と pivot の経路は別々に確認済みで、残る不足は評価器の質（甘い verdict・pivot を選ばない）である。
     2 時点の answer key に合わせて直すと過適合になるので、質は子 8 の pilot で C-mid・D-done・F-done を含む時点の盲検の評価と人の rubric で測る。それまで本番の controller は `shadow` のまま `enabled` にしない。
   - 案 2: 戦略を変える。checkpoint の行動の下限を決定的な信号で決める（子の報告の未達・要判断の印、反証、指標の after の欠落・悪化があれば、評価器の next が continue でも `escalate`）。
     LLM の評価は人への判断の材料にする。子 6 の中に WU 1〜2 個を足す（TS の規則と Rust の検証の変更）。
   - 案 3: 評価器の入力を直して再評価する。prompt に親の受け入れ条件の数値の目標と「未達を申告した子」の扱いを入れ、answer key を開いていない時点（C-mid・F-done）を含めて評価する。LLM の run 4〜6 回の承認が要る。
2. この WU の検査の不備（計画の問題。どれもこの WU の範囲の外）:
   - close-gate の check の `--run-ignored all -E 'test(/parent_checkpoint_/)'` が driver 用の seed `parent_checkpoint_blind_seed` を拾って落ちる。filter に `- test(=parent_checkpoint_blind_seed)` を足すか、seed の名前を `parent_checkpoint_` で始めない名前に変える（driver の `--exact` の名前も同時に変える）。
   - 同じ key の再実行では、WU の branch と範囲の基点（`CELERIS_WU_SCOPE_PATHS` の snapshot）が最初の run のまま残る。後の段の成果（fixture の比較の script・試験）を使うために統合先を取り込むと、範囲の check が統合先の 33 path を範囲外と数える。
     この WU の統合先からの差分は範囲の 4 path だけ（`git diff --name-only <統合先> HEAD`）。再実行の WU は新しい key で統合先から作るか、範囲の check を統合先との差分で数える。
3. 子 5 の穴（ADR D10。選ぶ版を実験の結果より先に書ける）: 見送りを続ける。採るなら、子 5 の gate に「`selected` の版の `ArtifactProduced` の seq が、参照する実験 task の終端の event の seq より後」の検査を足す（新しい表は要らない）。採否は親の closeout で人が決める。
4. 本番で controller を有効にするか: 第二ゲートを満たすまで、checkpoint の評価を含む mode `enabled` にしない。mode `shadow` で 1 案件だけ動かすのはよい（shadow では reviewer run が 0 件。試験 `parent_checkpoint_regression_shadow_no_reviewer_run`）。
5. worker の結果の読み方の不具合: `result.json` に `summary` と `yield` を併記すると、`crates/task-worker/src/result_report.rs` の `interpret_result_text`（優先順位 question > wait > summary > yield）が
   summary を先に見て done と読み、yield を黙って捨てる。子 6 では WU controller-checkpoint（run 2）と ts-checkpoint-rule で起き、未完の WU が done と読まれて再計画が要った。
   owner は `interpret_result_text`。両方あるときは形の誤り（`Error{retryable: true}`）にする案を提案する。試験は「summary と yield を持つ result.json が `Terminal::Done` にならない」。
6. `DECISION_GUARD` の GC: 害は 1 回の余分な写しなので、盲検の評価の 4 run では起きていない（記録が載った後に driver が止まる）。直すなら削除の trigger に rule `pc/checkpoint/act` の判断を除く条件を足す（migration が要る。store の WU で行う）。
7. `is_internal` の二重: `strategy::Reference::is_internal` を `pub` にし、`parent_checkpoint.rs` の写しを消す（子 2 の strategy の module を書ける WU で行う）。

## 本番への移行（人が行う）

- 必須の移行は無い。config の節 `[project_controller.checkpoint]` が無ければ既定値（`children_per_checkpoint = 2`・`budget_thresholds_pct = [50, 80]`・`max_evaluation_attempts = 2`）で動く。

- 第二ゲートが未達なので、この release で checkpoint の評価を本番の案件で `enabled` にしない（提案 4）。
- 有効にすると人が決めたときの手順は `docs/ops/project-controller.md` の「本番で有効にする人の手順」: (1) 対象の案件を `allowed_project_ids` に入れ mode `shadow` にし、
  `GET /api/v1/projects/{id}/controller/decisions` に `kind = evaluate`・`effect_state = suppressed` の行が出て reviewer run が増えないことを確かめる、(2) 既定値を変えるなら本番 config に節を書いて daemon を再起動する、

  (4) 戻すときは mode を `shadow` か `off` にする（走っている評価の run は最後まで走り、記録は消さない）。
- 評価の記録の path の確認（pivot-chain-test の未解決）: pivot-chain-test より前の release の `write_record` は評価の記録の `ArtifactRef.path` を絶対 path で書いた。その release が本番に入り、controller を `enabled` にした案件があったかを人が確かめる。
