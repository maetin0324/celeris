# 変更の規約（汎用）

## 規約
1. 症状が出た箇所に特例を足さず、原因を持つ owner（責務を負う module・関数）を直す（`symptom_fix_outside_owner`）。
2. 同じ仕様を二重に実装しない。同じ入出力の関数・経路が既にあれば、それを使うか直す（`duplicate_implementation`）。
3. 巨大な共通 interface（共通の型・trait・関数）に、特定の呼び出し元だけのための局所の hook や分岐を足さない（`local_hook_in_shared_interface`）。
4. 状態の正本を 2 つにしない。同じ状態を 2 か所に持つなら、どちらが正かを決め、もう一方は正本から導く（`dual_source_of_truth`）。
5. 承認の無い fallback・新旧切替の flag・互換分岐を増やさない。要るなら設計の記録で承認を得てから置く（`unapproved_fallback_or_switch`）。
6. 仕組みを置き換えたら、旧い経路・設定の欄・API の欄・試験・説明を同じ変更で消す（`removal_missing`）。
7. 移行のために旧い仕組みを一時的に残すときは、撤去の条件と撤去の責任者を書く。
8. 共通化は同じ意味のものだけにする。見た目が似ているだけで意味の違うものを 1 つにまとめない。
9. 許可された範囲で根本修正ができなければ、repair または replan を申告する。範囲の外に回避策を置かない。
10. 試験を足すときは、守る不変条件と、既存の試験ではそれを検出できない理由を書く。試験を消す・弱めるときは、契約を廃止したこと、または代わりの試験が同じ不具合を検出できることを示す（`test_change_unjustified`）。

## 実装前 brief
実装を始める前に、次の 7 項目を書く。
1. 根本原因: 何が原因で、症状はどこに出ているか。
2. 責務 owner: 原因を直すべき module・関数はどれか。
3. 既存の再利用先: 使える既存の実装・経路・試験はどれか。
4. 選択肢: 考えた案と、採用した案とその理由。
5. 新しい状態・分岐・fallback・port: 足すものと、それが要る理由。無ければ「無し」と書く。
6. 撤去対象: この変更で消す旧い経路・設定・API・試験・説明。
7. 不変条件: この変更の後も守られるべき条件と、それを確かめる試験。

repo の必須規則と健全性の guide に具体があれば、それに従う。
